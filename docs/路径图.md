## 0. 一句话定位

把基石语言（中文关键字、缩进语法）**裁成一个能在单片机上活下来的内核**，并给它起名 **砾**：

```
PC 上：  .jsh 源码 ──micc──▶  .jmb 微字节码
芯片上：.jmb ──libjishim(C99)──▶ 在 STM32F103C8T6 上执行
之后：  在同一个 VM 上长出任务、调度、延时、同步 —— 一个「砾写的」FreeRTOS 形态内核
```

不是把基石整个塞进 MCU，而是**先定一条能塞进去的线，再沿线往上长**。

### 名字与标识

| 项 | 名称 | 说明 |
|----|------|------|
| 语言 | **砾（LI）** | 本分支语言名；源码后缀仍为 `.jsh`（与基石同源） |
| 仓库 | `LI-JISHI-Micro` | `LI` = 砾，`Micro` = 面向 MCU |
| 能力档位 | **砾 Core** | v0 的明确子集，见 §5 |
| 编译器 | `micc` | 跑在 PC 上，`.jsh → .jmb` |
| 字节码 | `.jmb`（JMB v4） | 砾自己的微字节码，不复用基石的格式 |
| 运行时 | `libjishim` | C99，零依赖，可移植到任意裸机 |
| 内核（规划） | `砾-RT` | 建在 VM 之上的任务/调度层（JM8 起） |

## 1. 硬约束（先认清楚，再谈设计）

| 约束 | STM32F103C8T6 | 对设计的强制要求 |
|------|---------------|------------------|
| Flash | 64 KB | 字节码必须紧凑；VM + 应用 + HAL 要能共存 |
| SRAM | 20 KB | 值必须小；堆要静态；调用栈要可预算 |
| 主频 | 72 MHz | 解释器单指令开销必须按「几十个周期」算 |
| FPU | 无 | 浮点先不做，或只做库函数级软浮点 |
| MMU / 操作系统 | 无 | 不能依赖文件系统、动态加载、`malloc` |
| 中断 | NVIC | 中断里不能做不可预测的分配 / 回收 |
| 调试 | SWD + UART | 报错要能在串口上一眼看懂 |

**结论**：这不是「移植」，是「重新设计一套能对上的最小语义」。基石那套 24 字节指令、16 字节值、宿主回调模型，在这里全部要换掉。

## 2. 设计决策（D 系列，改一条要写理由）

| 编号 | 决策 | 理由 | 代价 |
|------|------|------|------|
| D001 | **编译在主机，执行在芯片** | MCU 上没有编译器生存空间；也让固件可以只带 VM | 需要两段工具链、需要 `.jmb` 契约 |
| D002 | **独立微字节码 `.jmb` v1** | 基石现有指令是 `op,a,b,c,line,col` 六个 int32 = 24 字节/条，且值全靠宿主句柄 | 不能直接复用基石的 VM / 字节码产物 |
| D003 | **4 字节值，低 3 位标签，29 位整数** | 20KB RAM 下 16 字节值不可接受；整数是控制类代码的绝对主力 | 整数范围 ±268,435,455；小数用独立堆对象（Q12 定点，值域约 ±524288） |
| D004 | **引用计数，无 GC（接受环泄漏）** | 即时回收、无停顿、实现小；20 KB RAM 放不下标记清扫。闭包与实例可以成环（闭包捕获含自身的容器、`本.自己 = 本`），这类块永久不回收 | 环引用会泄漏；反复造环最终报 `E017`（堆不足）而不是崩溃。文档（语言卡/字节码规格）显式写明 |
| D005 | **变长指令：1 / 2 / 3 字节** | 无操作数 1 字节；u8 操作数 2 字节；u16 跳转目标 3 字节 | 操作数上限：常量/名字/局部 ≤255，跳转/文件 ≤65535 |
| D006 | **砾 Core profile** | 语法跟基石一致，能力是明确子集；新增语法过一次「准入」 | 写基石全量程序会编译报错，需列差异清单 |
| D007 | **错误码 + 短中文文案** | Flash 里放不下长报错，也不做格式化拼接 | 报错信息比基石短；行列号靠可选调试表 |
| D008 | **协作式调度优先，抢占式后置** | 先证明「任务能切、能延时、能排队」，再谈 PendSV | 早期任务必须主动 `让出` |
| D009 | **中文关键字 + 全角标点归一化** | 保住基石的写法习惯，输入法不用切 | 词法器要在最前面做归一化 |
| D010 | **运行时 C99，零依赖** | 与 HAL/启动文件/链接脚本同语言；任何 MCU 都能带 | 需要宿主 C 编译器做本地验证 |
| D011 | **语言规范是单一事实来源，语言卡由它生成** | 砾是新语言，模型没有先验知识；手写第二份「给模型看的文档」必然与规范漂移 | 规范要补机器可读元数据（操作码表、内建表、语法产生式）+ 一个生成器 |
| D012 | **宿主工具链不进目标镜像** | 语言卡、包管理器、VSCode 扩展都不该占 MCU 的 Flash/RAM | 必须显式划出「运行时」与「工具链」的边界，产物分开发布 |
| D013 | **包格式带 ABI 版本，依赖用锁文件** | 换一版 `micc` 或换一套 native 函数表就跑不起来，是最贵的故障 | 要维护 ABI 版本号、兼容规则与锁文件的还原语义 |

```
                     └──────────────┬───────────────────────────────┘
                                    │ .jmb（二进制）
                                    ▼
   ┌─────────────────────────────────────────────────────────┐
   │  libjishim（C99，可移植核心）                              │
   │                                                         │
   │  jm_loader   读 .jmb（或直接吃内嵌数组）                   │

                                    ┌─────────▼─────────┐

                                    │ 任务 = 砾函数      │

                                    └───────────────────┘
```

`导入 模块` 编译期语法已落地：模块里的原生名字必须显式导入，名字拼错、参数个数不符、未导入就调用都在 `micc` 编译期报错（E112/E113/E115），不进入字节码；运行期仍按名字绑定到 `jm_native` 表。名字/参数个数的唯一事实来源是 `compiler/src/native_spec.rs`，C 侧 `runtime/include/jm_native_table.h` 由它生成七张表的宏，`micc --check-native` 与语言卡同源校验。

ADC / 定时器当前状态：编译期模块、生成表头、C 寄存器驱动、示例与主机回归（18 + 38 + 33 + 26 + 23）均已通过；ADC 零点（PA0 接 GND 读 0 / 0 mV）、ADC 满量程（PA0 接 3V3，末位 4094 属正常抖动）已上板（原始日志见 `docs/verification/`）。定时器计数上板时名义「1 kHz」有误（`PSC = 71999` 写进 16 位只剩 6463，实际约 11.138 kHz），2026-11-08 已改为 SysTick 毫秒基准、TIM2 只做 1 MHz 自由运行，见 [原生函数表.md](原生函数表.md) §11.3。

**中断表（2026-11-08 收尾）**：`f103_exti` 四项——`中断绑定` / `中断触发` / `中断计数` / `中断解除`，引脚 0–4 对应 EXTI0–4。端口层 `EXTI_IRQHandler` 只清挂起位、计数并回调板级 `irq_post_from_isr`，后者只发一次 `jmk_queue_send_from_isr`；**ISR 里不执行任何字节码、不进 VM、不进 native 分派**，ABI v1 的「中断不得直调 native」保持不变。板上没有用户按键（PC13 是 LED 输出），到板证据用 `EXTI_SWIER` 软件触发，走的是同一条 `EXTI → NVIC → ISR → 队列 → 任务` 路径；PA0–PA4 同时配成下拉输入，接 3V3 即可用真实上升沿，`.jsh` 不用改。上板实测 18 行输出与主机逐行一致（`收到 = 0/1/0/1`，计数 2/2），`vm` 栈峰值 368 B / 1024 B。
JM13 + JM14 运行时增量：同一 `异常` 示例 **25 616 → 28 052 B Flash（+2 436 B）**，RAM **14 644 → 14 652 B（+8 B）**；
`类` 示例整包为 **27 956 B Flash（42.7%）/ 14 652 B RAM（71.5%）**。

真机验收依据（ST-LINK 烧 `0x08000000` → CH340 串口录制，脚本见 [原生函数表.md](原生函数表.md) 11.1）：

- （导入 引脚 轮次）启动即打印 `[原生] 板级函数表已登记：f103_board`；SWD 读 `g_nentries=5`、`g_ntables=1`，ICSR / CFSR / HFSR 全 0。加入 ADC / 定时器后实际为 `f103_board, f103_adc, f103_timer`、`g_nentries=10`、`g_ntables=3`，已上板复核。
- **砾代码点灯**：示例阶段 PC13 亮/灭各 4 次（各 400 ms），日志为 8 行 `LED 亮` / `LED 灭`，随后 `翻转后，引脚读 = 0`、`板级示例结束`、`[砾] 程序正常结束`。这一段全部由 `.jsh` 的 `引脚写 / 引脚翻转` 驱动，C 只提供引脚层，没有 C 示例任务参与。
- **内核 C 示例任务闪烁**：`[内核] 启动调度器…` 之后 `task_led` 每 200 ms 翻转，串口同步输出 `[同步] 收到 seq=N`；实测 589 行 / 125 秒 ≈ 212 ms 行距，`seq` 逐 1 递增、`累计 == seq`、零丢弃，两段行为并存。
- `引脚读 = 0` 的语义：示例最后一轮是 `引脚写(13, 1)`（高电平、灭），`引脚翻转` 后为低电平，故读回 0，与「PC13 低电平点亮」一致（此前主机替身表读到 1 是替身自身初值，不代表硬件语义）。
- 录制期间用户主动按了两次复位（seq 从 247、158 各回到 1），两段启动输出逐字一致，用于核验行为可复现性；**不是供电抖动或接触不良**。

**H1 与语言规范的关系（单一事实来源）**

- 规范的载体是机器可读的：`opcodes.rs`（操作码）+ 内建函数表 + 语法产生式；`docs/语言卡.md` 与 `spec/langcard.json` 是**生成物**，不是手写副本。
- 版本演进：卡片带 `lang_version`、`bytecode_magic`、`bytecode_version`、`native_abi_version` 四个字段（均从编译期常量渲染）；`abi_version` 已弃用，仅为旧消费者保留。`0.x` 每发一版重新生成一次，`micc --check-langcard` 比对生成结果与入库文件，不一致就失败。
- 分层：语言卡属于**宿主工具链**，只在 PC 上生成与分发，不链进固件；固件里只留错误码与短文案（D007 已定）。

### 宿主侧依赖关系

```
JM1 ──▶ H1（语言卡，可立即开工）
H2 ──▶ H3（扩展的「运行/烧录」按钮就是调 H2 的脚本）
JM7 + JM8 ──▶ H4a（源码包最小切分，已落地）
JM10 ──▶ H4b（`.jmb` 内嵌/归档、二进制包，已落地；多 `.jmb` 链接不做）──▶ H5（索引与托管）
H2 + JM7 ──▶ H6（Arduino：先文档，后库桥接；core 不做）
```

**H6：Arduino 集成（结论：现在只写文档，不建 core）**

两种「集成」不是一回事，成本和风险差一个数量级：

| 含义 | 谁负责构建 | 砾的位置 | 现实成本 |
|------|-----------|----------|----------|
| **A. 上传/烧录通道** | Arduino（`arduino-cli`/IDE）编 `.ino` | 砾只交付 `.bin/.hex` | 低：本质是换一个烧录前端 |
| **B. 砾做成第三方 core** | Arduino 的 `platform.txt` recipe 全流程 | 砾要提供 core + variant + 板级包 | 高：等价于自建一套板级支持包 |

**A 路：把 Arduino 当上传通道**

- `arduino-cli upload` 只是按 `platform.txt` 的 `upload.recipe` 调外部命令；板卡不支持 SWD 就没有可用 recipe。F103C8T6 的常见包（STM32duino）默认走串口 bootloader 或 ST-LINK/OpenOCD。
- 本板 Flash 出厂为空、没有 Arduino bootloader，A 路只能落回 `stlink`/`openocd` —— 与现有 [flash-firmware.ps1](../tools/flash-firmware.ps1)（CubeProgrammer，按段擦 sectors 0–17）成为两条并行前端，擦除粒度与复位策略不一致。
- 编译侧：`arduino-cli` 只编 sketch + core。想让砾产物进 sketch，只能把 `libjishim` + `jm_blob.c` 当 `src/` 编，这要求 core 提供 `Arduino.h`/`main`/时钟初始化，与现有裸机 startup、链接脚本、向量表**两套 `main`** 冲突。
- **结论**：不作主通道。现有 `build-firmware.ps1 → flash-firmware.ps1` 已覆盖烧录，再套一层收益接近 0、维护是双份。

**B 路：砾做成 Arduino core**

| 约束 | 具体内容 |
|------|----------|
| 构建模型 | 编译单位是 sketch + core + variant + library；`platform.txt` 用 `recipe.c.o.pattern` / `recipe.cpp.o.pattern` / `recipe.c.combine.pattern` 拼命令。砾源码不是 C/C++，必须在 `recipe.hooks.prebuild.pattern` 里插一次 `micc` 生成 `.jmb`，再把产物当资源链接进去 —— 可行，但属于「非标准构建物」，且 Windows/Unix 两套 shell 都要成立。 |
| 工具链 | 平台包绑定自己的 `compiler.path`（STM32duino 是 arm-none-eabi-gcc），能容纳 C99 运行时；但 `micc` 是 PC 上的 Rust 二进制，**不属于**这个工具链，只能作为平台包外的预编译依赖分发，并与 H2 一样锁版本。 |
| 板级变体 | 每块板要 `boards.txt`（时钟/Flash/RAM 上限）+ `variants/<板>/variant.h`（引脚）+ 链接脚本。砾现在只有 F103C8T6 一套，扩板等于每块重做，维护面随板卡数线性增长。 |
| 库生态假设 | Arduino 库默认要 C++、`Print`/`Stream`、`String`、`millis()`、动态分配、全局构造器；砾是裸机 C99、静态堆、无 C++ 运行时。这些库**进不了 `.jmb`**，只能留在 C 侧当外设驱动。所以「做成 core 后能直接用 Arduino 库」这个卖点是假的。 |
| 与现有流程 | `platform.txt` 若接管烧录后端，会和 CubeProgrammer「按段擦除、不整片擦除」策略冲突；SWD 读取、复位、选项字节检查这些能力在 Arduino IDE 里没有对应位置。 |

**阶段建议**

| 阶段 | 做什么 | 成本 | 何时做 | 返工风险 |
|------|--------|------|--------|----------|
| H6.0 | 本评估 + 结论进路径图 | 已完成 | 现在 | 无 |
| H6.1 | 文档级：给出 `arduino-cli` 上传现有固件的等价命令（不写集成代码） | 极低 | 现在或随 H2 | 低 |
| H6.1a | 已完成：[H6.1-Arduino上传.md](H6.1-Arduino上传.md)。结论是「能传但不划算」：需装 STM32duino 平台包（数百 MB）才有一条 upload recipe；给出 FQBN/`--input-file` 命令模板、与 CubeProgrammer 同为 SWD 前端的关系、以及擦除/复位/选项字节不能混用的边界。命令未在本机执行（无 `arduino-cli`/`openocd`），带 `<...>` 处须用 `board details` 查实 | 已完成 | 2026-11-08 | 无 |
| H6.2 | 库形式桥接：`libjishim` + `jm_blob.c` 包成 STM32duino 的 `src/` 库，`setup()` 调 `jm_run`，`loop()` 空转 | 中 | **等 JM7 的 native 函数表冻结之后** | 中：与 ST-LINK 流程并存，需明确谁负责复位/擦除 |
| H6.3 | 独立 core（`boards.txt` + `platform.txt` + variant 全套） | 高 | 不排期，除非出现明确外部需求 | 高：Arduino 平台规范逐年演进；库生态假设不成立，卖点兑现不了 |

**前置条件**

- H6.1：无。
- H6.2：`libjishim` 的 C API 稳定（`jm_run` 的可重入边界、`jm_last_error` 的中断语义）——**Native ABI v1 已冻结（JM7）**；剩余是 `jm_blob.c` 生成能脱离 `build-firmware.ps1` 单独调用。
- H6.3：先有 Arduino 兼容层（`Arduino.h`、`Print`、`millis`/`delay`、`main` 入口收敛）——这本身已是独立里程碑，不符合「顺手做」。

**风险**

| 风险 | 触发信号 | 应对 |
|------|----------|------|
| 两套烧录流程互相踩 | Arduino 上传后 CubeProgrammer 校验失败 / 选项字节被改 | Arduino 只管上传；擦除与复位策略仍以 `flash-firmware.ps1` 为准，platform 包不碰 option bytes |
| 平台版本漂移 | 换 board manager 版本后 core 编不过 | H2 锁版本；core 面尽可能小 |
| 把「能用 Arduino 库」当目标 | 用户拿 Wire/SPI 库直接进砾 | 写清边界：Arduino 库只能在 C 侧当外设驱动，不进 `.jmb` |
| 维护面随板卡爆炸 | 每加一块板就要一套 variant | 只承诺 F103C8T6，其它板按「用户自带 core」处理 |


**为什么这样排**

1. **H1 最先，且现在就能开工。** 它只依赖已经冻结的 JM1 契约和 JM2 的 `--dump`，不碰芯片。砾是新语言，模型没有先验知识，这一项边际成本最低、对「模型能不能一次写对」的收益最直接。它还必须赶在语言能力扩张（JM11 小数、JM12 闭包、JM13 异常、JM14 类）之前把「规范 → 卡片」的生成链路建起来，否则每加一个特性都要手工补两遍文档。
2. **H2 第二。** §8 里「本机没有 C 编译器」不是假设，已经真实发生过；把工具链封成绿色包/容器，是把这条风险一次性消掉，也是 CI 与 H3 的前置。
3. **H3 第三。** 高亮与格式化只需要语法，但诊断与跳转依赖 `micc --check` 的稳定错误码（D007）和 `.jmb` 调试表，运行/烧录按钮本质上就是调 H2 的脚本——所以必须排在 H2 之后，但不必等 H4。
4. **H4 拆两段。** 源码包这一段（本地路径依赖、源码级合并、单 `.jmb`）不依赖 JM10，已经先行落地；涉及 `.jmb` 归档的那一段（H4b）已在 JM10 的打包规则固化后落地（2026-11-09）。二进制包只发预编译产物、不允许声明依赖；**多 `.jmb` 链接决定不做**，理由见 [包规范.md](包规范.md) §11。
5. **H5 最后。** 索引与托管是 H4 的放大器；包规范没稳定就先建仓库，只会把错误固化成 URL。它同时是「与现有外置包管理站衔接」的落点：两边共用同一份 schema，不维护第二套目录。

## 6. 资源预算（整包实测）

实测条件：`arm-none-eabi-gcc 13.3.1`，`-Os -mcpu=cortex-m3 -mthumb`，**含启动文件、JMK 内核、USART/ADC/TIM/I2C/SPI 驱动、运行时与内嵌 `.jmb`**。

| 项目 | 实测 | 占芯片 | 说明 |
|------|------|--------|------|
| Flash（`类` 示例整包） | 44 328 B | 67.64% / 64 KB | 2026-11-09 复测（任意引脚扩容后）；CI 用此包；含运行时 + JMK + 驱动 + 内嵌 `.jmb` 953 B |
| Flash（`board\OLED文字` 整包） | 47 356 B | 72.26% / 64 KB | 2026-11-09 复测；**当前最大示例**（I2C/SSD1306）；内嵌 `.jmb` 3 983 B |
| RAM（bss，整包） | 17 404 B | 84.98% / 20 KB | 含 `jm_heap` 6 144 B、JMK 栈池 3 200 B、`jm_state` 6 300 B、静态空闲栈 256 B、SPI 状态 16 B、引脚电平表 48 B；各示例 bss 相同 |
| 剩余 RAM | 3 076 B | 15.02% | **= 20 480 − 17 404**；给 C 栈与中断（链接脚本要求主栈 ≥ 2 048 B） |
| 剩余 Flash | 18 180 B | — | **= 65 536 − 47 356**（当前最大示例）；加功能前先看 `jishim.map` |
| 宿主工具链（H1–H5） | 0 B | 0 B | 全在 PC 上，不进目标镜像（D012） |

> 结论：**运行时 + 内核 + 驱动装得下 F103C8T6**；RAM 余量 **3 076 B**，是最紧的约束；Flash 余量 18 180 B 相对宽松。往后报余量一律用「当前总量 − 当前占用」，不混旧基线。
> 注：本表 2026-11-09 按当前源码重新实测（`类` 44 328、`OLED文字` 47 356）。SPI（N10）相对 I2C 收尾态 **+1 712 B Flash / +16 B RAM**；任意引脚扩容（N22 前置）再 **+40 B Flash / +48 B RAM**（`g_pin_out[48]`），两个示例增量相同。此前的 37 220 / 37 316 / 37 760 / RAM 17 060 是 JM11–JM14 交付前的快照，**已作废**，不要再作为预算依据；`异常` 与 `数据采集器` 两包本轮未逐一复测。

## 7. 与基石主干的关系

1. **语法同源，语义是子集**：关键字、缩进、全角标点归一化、显示规则都对齐基石；不另造一套中文写法。
2. **代码不合并**：砾有自己的字节码与 VM，不试图让基石的 Rust VM 跑在 MCU 上。共享的是**规格**，不是实现。
3. **差异显式化**：任何「基石能跑、砾不能」的写法，`micc` 必须报专门的错误码（例如 `E117 闭包捕获变量只读`、`E103 继承不支持`），不静默降级。
4. **版本线独立**：从 `0.1.0` 起，按 `0.x` 演进；`1.0` 的判据是「JM10 完成 + 差异清单冻结」。
5. **回归对齐**：JM4 起，同一份 `.jsh` 在砾主机端口与基石解释器的输出做逐字节对比（只比两边都支持的子集）。

## 8. 风险与备选

| 风险 | 触发信号 | 备选 |
|------|----------|------|
| 20KB RAM 不够 | 跑两个任务就堆耗尽 | 缩小堆、把字符串放 Flash、栈槽按需分配 |
| 引用计数抖动 | 频繁分配释放导致碎片 | 对象池 / 固定大小类；标记清扫仅在 RAM 允许时评估（当前 D004 已定：无 GC、接受环泄漏） |
| 抢占式切换复杂 | PendSV 保存/恢复状态出错 | 先只交付协作式（JM8），抢占式推迟 |
| 无 FPU | 软浮点拖慢控制环 | 提供定点数类型（Q15/Q31） |
| 本机没有 C 编译器 | 无法在 PC 验证 | 预编译工具链 / Docker / CI |
| 语法漂移 | 砾与基石写法分叉 | 差异清单 + 对齐测试进 CI |
| 模型写不对砾 | 生成代码语法/语义错误率高，反复返工 | H1 语言卡 + 可编译示例片段；`--check-langcard` 进 CI，卡片不漂移 |
| 工具链版本漂移 | 换台机器就编不过，或产物不一致 | H2 绿色包 + 容器镜像；版本号与校验值入库 |
| 包依赖冲突 | 两个包互相顶版本，现场才发现 | H4 锁文件 + 编译期 ABI 校验（`micc` 报 E129，安装阶段不校验 ABI） |
| **原生表位将用尽** | 现在 **7 张表 / 32 项**，上限 8 张 / 64 项：**项数宽松，余 1 张表**（PWM 已并入 `定时器`；I2C 与 SPI 都在 `总线`，不再新开表） | 上限是运行期策略常量（`JM_NATIVE_MAX_TABLES` / `JM_NATIVE_MAX_ENTRIES`），抬高不必升 ABI，但要同步 `compiler/src/native_spec.rs`、`runtime/include/jm_native.h`、语言卡与包清单的 `原生ABI` 字段；硬墙是 8 位原生 id（`JM_NATIVE_ID_BASE = 64`，最多 191 项）。详见 [设计-原生表容量与ABI.md](设计-原生表容量与ABI.md) |
