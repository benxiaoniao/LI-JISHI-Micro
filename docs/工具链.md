# 可复现的编译环境

目标：换一台机器，只按本文五步就能编译、不再出现「本机没有 C 编译器」。

## 锁定版本

清单在 [tools/toolchains/toolchain.lock.json](../tools/toolchains/toolchain.lock.json)（schema `jishi.toolchain.lock/1`）。

| 名字 | 版本 | 用途 | 来源 |
|---|---|---|---|
| `arm-none-eabi` | 13.3.1（xPack 13.3.1-1.1，20240614） | 交叉编译固件 | xPack 发布页，`tools/fetch-toolchain.ps1` 可自动下载 |
| `host-gcc` | 16.1.0（MinGW-W64 ucrt posix-seh） | 主机侧编译 C 验证 | 手动放置（[MSYS2](https://www.msys2.org/) / [winlibs](https://winlibs.com/) 装同版本） |
| `node` | 18+（可选） | 构建/测试 VS Code 扩展 | [nodejs.org](https://nodejs.org/) |
| `STM32CubeProgrammer` | 任意近期版本（可选） | SWD 烧录 | [ST 官网](https://www.st.com/en/development-tools/stm32cubeprog.html) |

清单同时记录关键二进制的 sha256，用来确认「装的是同一份二进制」。xPack 不发布压缩包校验文件，所以 `archive.sha256` 为 `null`，下载后按解压出来的二进制哈希校验。

## 目录约定

工具链放在**外部缓存目录**（纯 ASCII 路径），不入库：

```
%LOCALAPPDATA%\jishi\toolchains\      # 本机默认位置，可用 JM_TOOLCHAIN_ROOT 改根目录
  toolchain.lock.json                 # 入库原件在 tools/toolchains/toolchain.lock.json
  arm-none-eabi\bin\*.exe             # 约 1.3 GB（解压后）
  host-gcc\bin\gcc.exe
```

仓库内也保留了同名位置（`tools/toolchains/<名字>/bin`），但它只在仓库路径是**纯 ASCII** 时才可用。

**为什么默认不放进仓库**：这是个真实踩过的坑。MinGW 版 `gcc`/`ld` 内部用 ANSI 文件 API 定位 `crti.o`、`-lgcc`、multilib 目录，仓库路径里带中文（如 `D:\code\基石·微（砾）`）时，链接会报：

```
cannot find .../crti.o: No such file or directory
cannot find -lgcc: No such file or directory
```

同样的二进制放到 `C:\Users\<名>\AppData\Local\jishi\toolchains\` 就正常。所以「工具链的位置」必须是 ASCII。

`tools/toolchains.ps1` 的解析顺序是：**包内 `tools/toolchains/<名字>/bin` → 外部缓存 → 环境变量（`JM_ARM_GCC` / `JM_HOST_GCC` / `JM_ARM_SIZE`）→ PATH**。前两者都不依赖 PATH，环境变量只作临时指定。

## 换台机器怎么起

1. 装 [Rust](https://rustup.rs/)（`rustup`）与 PowerShell 5.1 以上；`git clone` 本仓库。
   只做编辑器扩展时另需 [Node.js](https://nodejs.org/) 18+。
2. 拉交叉工具链（自动下载 + 哈希校验 + 解压到 `%LOCALAPPDATA%\jishi\toolchains\arm-none-eabi`）：

   ```powershell
   powershell -ExecutionPolicy Bypass -File tools\fetch-toolchain.ps1
   ```

   仓库路径是纯 ASCII、想把工具链跟着仓库走时，加 `-Bundle`。已装过时脚本会提示并跳过（退出码 0）。

3. 放主机 gcc：从 [MSYS2](https://www.msys2.org/)（`mingw-w64-x86_64-gcc`）或
   [winlibs](https://winlibs.com/) 装 MinGW-W64 16.1.0，把整个 `bin` 目录放到
   `%LOCALAPPDATA%\jishi\toolchains\host-gcc\bin`（或直接设置 `JM_HOST_GCC`）。
   `host-gcc` 没有自动下载，脚本会明确告诉你这一步要手动做。
4. 自检，看是否全部 `[OK]`：

   ```powershell
   powershell -ExecutionPolicy Bypass -File tools\toolchains.ps1
   ```

   通过后直接 `.\tools\build-firmware.ps1` 即可。
5. 只烧板时才需要：装 [STM32CubeProgrammer](https://www.st.com/en/development-tools/stm32cubeprog.html)
   （或已装 STM32CubeIDE），把 `STM32_Programmer_CLI.exe` 的完整路径设进环境变量
   `STM32_PROGRAMMER_CLI`，或改 `tools\flash-firmware.ps1` 顶部的 `$cli`。
   CubeProgrammer 安装目录下通常是 `bin\STM32_Programmer_CLI.exe`。

## 绿色包（离线分发，H2）

已经把两条工具链装好的机器可以打成 zip，另一台机器解压即用、不联网：

```powershell
# 打包（默认 host-gcc + arm-none-eabi，约 2 GB；Level=Fastest 几十秒）
powershell -ExecutionPolicy Bypass -File tools\pack-toolchains.ps1
# 只校验、不出包
powershell -ExecutionPolicy Bypass -File tools\pack-toolchains.ps1 -CheckOnly
```

产物：`build\toolchains\jishi-toolchains-<lock 日期>.zip`，内含

```
host-gcc/bin/…            # 主机 gcc
arm-none-eabi/bin/…       # 交叉工具链
清单.txt                  # 版本、binutils 版本、关键文件 sha256（来自 toolchain.lock.json）
```

使用：

```powershell
# 解压到纯 ASCII 路径（必须；中文路径下 MinGW 版 gcc 会找不到 crti.o / -lgcc）
Expand-Archive build\toolchains\jishi-toolchains-2026-11-07.zip D:\jishi-toolchains
$env:JM_TOOLCHAIN_ROOT = "D:\jishi-toolchains"
powershell -ExecutionPolicy Bypass -File tools\toolchains.ps1   # 应全部 [OK]
.\tools\build.ps1
.\tools\build-firmware.ps1 -Example 类
```

`tools\toolchains.ps1` 的查找顺序是「包内 `tools/toolchains/<名字>` → `JM_TOOLCHAIN_ROOT` 缓存 → `JM_HOST_GCC`/`JM_ARM_GCC` → PATH」，所以设置 `JM_TOOLCHAIN_ROOT` 后不会再读本机原有缓存。

## 容器镜像（Dockerfile，已实测）

仓库根目录的 `Dockerfile` 用 `mcr.microsoft.com/powershell:7.4-ubuntu-22.04`，apt 装 host gcc（build-essential），Rust 用 rustup 固定 **1.98.1**（与开发机同版本；Ubuntu 22.04 发行版 rustc 1.75 读不了 `Cargo.lock` v4），arm-none-eabi 用 lock 里固定的 xPack Linux 包放进 `/opt/jishi-toolchains`，再跑 `build.ps1 -SkipTests` 与 `build-firmware.ps1 -Example 类`。

```bash
docker build -t jishi-build .
docker run --rm jishi-build
```

**实测（2026-11-09，Docker Desktop 29.9.2 / linux 引擎）**：

| 项 | 结果 |
|----|------|
| `docker build` | 通过；镜像 **2.88 GB**（含 280 MB xPack 与 Rust 工具链） |
| 固件体积 | 容器内 **FLASH 42 576 B / RAM 17 340 B**（SPI 落地前的口径；SPI 后开发机为 44 288 / 17 356），与开发机同口径 |
| 运行 | 容器内 `./build/jmrun ./build/类.jmb` 输出与开发机一致 |
| 回归 | **未跑**：`test-*.ps1` 仍按 Windows 路径（`micc.exe`）写，容器里只验证「能构建」 |

为让同一套脚本能在 Linux 上跑，构建脚本做了最小跨平台化：路径统一正斜杠、可执行后缀走 `$ExeSuffix`（`toolchains.ps1` 导出）、非 Windows 主机运行时用 `-std=gnu99`（`-std=c99` 会隐藏 `popen`/`clock_gettime`/`nanosleep`）。Windows 侧已复测：`build.ps1` 与 `build-firmware.ps1` 结果一致（当时口径 42 576 / 17 340；SPI 落地后为 44 288 / 17 356）。

边界：容器内的 host gcc 是发行版版本，与开发机锁定的 MinGW 16.1.0 不一致，因此镜像里设 `JM_SKIP_TOOLCHAIN_CHECK=1`；体积与体积报告口径仍以开发机实测为准。`build/`、`compiler/target/` 由 `.dockerignore` 排除，不进入构建上下文。


## 固件构建脚本的开关

`tools/build-firmware.ps1` 有两个参数：

| 参数 | 默认 | 作用 |
|---|---|---|
| `-Example` | `你好` | 选 `examples\<名字>.jsh` 编进固件 |
| `-Define` | 空 | 追加一个/多个 C 宏，原样拼进交叉编译命令行 |

```powershell
.\tools\build-firmware.ps1                                   # 默认：诊断开、值栈峰值观测关
.\tools\build-firmware.ps1 -Define "-DJM_STACK_DIAG=0"       # 关诊断，测体积下限
.\tools\build-firmware.ps1 -Define "-DJM_STACK_WATERMARK=1"  # 开值栈峰值观测（串口多打一行峰值）
```

`-Define` 是数组参数，传多个宏写成 `-Define "-DX=1","-DY=2"`。它只影响这一次构建，不改源文件里的默认值；体积对照的两档就靠它，别手改 `#define`。

`JM_STACK_WATERMARK` 默认 **0**（关）：它只用于预算实测，不该常驻固件（`PUSH_V` 每次多一条比较）。要数字时单独构建一档。

### 内嵌字节数组由 `micc` 生成

第 4 步不再由 PowerShell 内联拼 C 数组，而是调用：

```powershell
micc --emit-blob build\stm32\app.jmb -o build\stm32\jm_blob.c
```

- 输出固定符号 `jm_app_jmb[]` 与 `jm_app_jmb_len`；每行 12 字节、4 空格缩进、大写两位十六进制。
- 默认输出与输入同目录的 `jm_blob.c`，用 `-o` 可指定。
- 格式只有这一份实现，`build-firmware.ps1` 与外部工具（如 Arduino 库、自定义构建）都用同一命令，不会漂移。

## 校验

- 版本：`tools/toolchains.ps1` 直接运行时把实测版本与清单比对，不符会打印 `[问题]` 并以退出码 1 结束。
- 哈希：`tools/toolchains.ps1` 对本地已有副本逐个核对清单里的 sha256；`tools/fetch-toolchain.ps1` 安装后再核对一遍，不符即中止。
- 已装好但想复核：直接重跑 `fetch-toolchain.ps1`，脚本会提示「目录已存在」并跳过（退出码 0）；要强制重装加 `-Force`。

## 在 CI 里用

工作流在 [.github/workflows/ci.yml](../.github/workflows/ci.yml)，跑在 GitHub 托管的 `windows-latest` 上：

| 项 | 做法 |
|---|---|
| Shell | `pwsh`（PowerShell 7）。Windows PowerShell 5.1 读无 BOM 的 UTF-8 脚本会把中文参数读坏，CI 不碰这个坑 |
| 主机 gcc | `msys2/setup-msys2@v2` 装 `mingw-w64-x86_64-gcc` 并 `path-type: inherit`。**版本与开发机锁定的 16.1.0 未必一致**，所以 `tools/toolchains.ps1` 不作为 CI 门禁（它被 dot-source 时只记录 `[问题]`，不退出） |
| arm-none-eabi | 缓存 `%LOCALAPPDATA%\jishi\toolchains\arm-none-eabi`（key 取 `toolchain.lock.json` 的哈希）；缓存未命中才跑 `tools/fetch-toolchain.ps1`，安装后仍按清单里的 sha256 逐个核对 |
| 门禁 | `tools/build.ps1`（含全部回归）+ `micc --check-langcard` + `micc --check-native` + `build-firmware.ps1 -Example 类` |
| 体积 | `tools/size-report.ps1 -Label "类示例"`，与入库基线 `tools/size-baseline.json` 对比；elf/bin/hex/map 与 `size-report.json` 作为 artifact 上传 |

`--check-langcard` 与 `tools/test.ps1` 已对 CRLF 做归一化，`core.autocrlf` 为 `true` 的检出不会因此假失败。

CI **不能**覆盖（缺硬件）：

- ST-LINK 烧录与真机启动（`tools/flash-firmware.ps1`）
- 串口采集与实机时序（`tools/capture-serial.ps1`）
- ADC / PWM / 定时器的电气行为，以及 20 KB SRAM 的真实运行余量

注意 CI 的 checkout 路径也要是 ASCII（`/home/runner/work/...` 天然满足；自建 runner 别放在中文目录）。

## 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 提示「找不到 arm-none-eabi-gcc」 | 包内没有、缓存没有、PATH 也没有 | 跑 `fetch-toolchain.ps1`，或设 `JM_ARM_GCC` |
| 提示「版本不符」 | 装了别的版本 | 按清单版本重装；临时放行可设 `JM_SKIP_TOOLCHAIN_CHECK=1`（不推荐） |
| 链接报 `cannot find crti.o` / `cannot find -lgcc` | 工具链在中文/非 ASCII 路径下 | 装到 `%LOCALAPPDATA%\jishi\toolchains\`（默认就是），见上文「目录约定」 |
| 链接时找不到 `nano.specs` | 工具链目录被裁剪 | 用完整发布包，别只拷 `bin` |
| 解压后仍是空目录 | 压缩包多一层目录 | 脚本已自动下钻找 `bin/<exe>`，若失败请贴出目录结构 |
