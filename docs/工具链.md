# 可复现的编译环境

目标：换一台机器，只按本文四步就能编译、不再出现「本机没有 C 编译器」。

## 锁定版本

清单在 [tools/toolchains/toolchain.lock.json](../tools/toolchains/toolchain.lock.json)（schema `jishi.toolchain.lock/1`）。

| 名字 | 版本 | 用途 | 来源 |
|---|---|---|---|
| `arm-none-eabi` | 13.3.1（xPack 13.3.1-1.1，20240614） | 交叉编译固件 | xPack 发布页，`tools/fetch-toolchain.ps1` 可自动下载 |
| `host-gcc` | 16.1.0（MinGW-W64 ucrt posix-seh） | 主机侧编译 C 验证 | 手动放置（MSYS2 / winlibs 同版本） |

清单同时记录关键二进制的 sha256，用来确认「装的是同一份二进制」。xPack 不发布压缩包校验文件，所以 `archive.sha256` 为 `null`，下载后按解压出来的二进制哈希校验。

## 目录约定

工具链放在**外部缓存目录**（纯 ASCII 路径），不入库：

```
%LOCALAPPDATA%\jishi\toolchains\      # 本机默认位置，可用 JM_TOOLCHAIN_ROOT 改根目录
  toolchain.lock.json                 # 入库原件在 tools/toolchains/toolchain.lock.json
  arm-none-eabi\bin\*.exe             # 约 1.3 GB（解压后）
  host-gcc\bin\gcc.exe
```

仓库内也保留了同名位置（`tools/toolchains/<名字>/bin`），但它只在仓库路径是**纯 ASCII** 时才可用。

**为什么默认不放进仓库**：这是个真实踩过的坑。MinGW 版 `gcc`/`ld` 内部用 ANSI 文件 API 定位 `crti.o`、`-lgcc`、multilib 目录，仓库路径里带中文（如 `D:\code\基石·微（砾）`）时，链接会报：

```
cannot find .../crti.o: No such file or directory
cannot find -lgcc: No such file or directory
```

同样的二进制放到 `C:\Users\<名>\AppData\Local\jishi\toolchains\` 就正常。所以「工具链的位置」必须是 ASCII。

`tools/toolchains.ps1` 的解析顺序是：**包内 `tools/toolchains/<名字>/bin` → 外部缓存 → 环境变量（`JM_ARM_GCC` / `JM_HOST_GCC` / `JM_ARM_SIZE`）→ PATH**。前两者都不依赖 PATH，环境变量只作临时指定。

## 换台机器怎么起

1. 装 Rust（`rustup`）与 PowerShell 5.1 以上；`git clone` 本仓库。
2. 拉交叉工具链（自动下载 + 哈希校验 + 解压到 `%LOCALAPPDATA%\jishi\toolchains\arm-none-eabi`）：

   ```powershell
   powershell -ExecutionPolicy Bypass -File tools\fetch-toolchain.ps1
   ```

   仓库路径是纯 ASCII、想把工具链跟着仓库走时，加 `-Bundle`。

3. 放主机 gcc：从 MSYS2 或 winlibs 装 MinGW-W64 16.1.0，把整个 `bin` 目录放到
   `%LOCALAPPDATA%\jishi\toolchains\host-gcc\bin`（或直接设置 `JM_HOST_GCC`）。
   `host-gcc` 没有自动下载，脚本会明确告诉你这一步要手动做。
4. 自检，看是否全部 `[OK]`：

   ```powershell
   powershell -ExecutionPolicy Bypass -File tools\toolchains.ps1
   ```

   通过后直接 `.\tools\build-firmware.ps1` 即可。

## 校验

- 版本：`tools/toolchains.ps1` 直接运行时把实测版本与清单比对，不符会打印 `[问题]` 并以退出码 1 结束。
- 哈希：`tools/toolchains.ps1` 对本地已有副本逐个核对清单里的 sha256；`tools/fetch-toolchain.ps1` 安装后再核对一遍，不符即中止。
- 已装好但想复核：删掉目录重跑（或加 `-Force`）。

## 在 CI 里用

CI 不需要 PATH 里预先有 gcc，只要把工具链装到 ASCII 路径再调脚本即可：

```powershell
.\tools\fetch-toolchain.ps1
.\tools\toolchains.ps1          # 自检，非 0 就直接失败
.\tools\build-firmware.ps1
.\compiler\target\release\micc.exe --check-langcard
```

注意 CI 的 checkout 路径也要是 ASCII（`/home/runner/work/...` 天然满足；自建 runner 别放在中文目录）。

## 常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 提示「找不到 arm-none-eabi-gcc」 | 包内没有、缓存没有、PATH 也没有 | 跑 `fetch-toolchain.ps1`，或设 `JM_ARM_GCC` |
| 提示「版本不符」 | 装了别的版本 | 按清单版本重装；临时放行可设 `JM_SKIP_TOOLCHAIN_CHECK=1`（不推荐） |
| 链接报 `cannot find crti.o` / `cannot find -lgcc` | 工具链在中文/非 ASCII 路径下 | 装到 `%LOCALAPPDATA%\jishi\toolchains\`（默认就是），见上文「目录约定」 |
| 链接时找不到 `nano.specs` | 工具链目录被裁剪 | 用完整发布包，别只拷 `bin` |
| 解压后仍是空目录 | 压缩包多一层目录 | 脚本已自动下钻找 `bin/<exe>`，若失败请贴出目录结构 |
