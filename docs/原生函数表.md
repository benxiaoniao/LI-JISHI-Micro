# 原生函数表（Native ABI v1）

> 面向：写 native 模块的人（C 侧）、写包管理器的做法（H4）、Arduino 桥接（H6.2）
> 代码：`runtime/include/jm_native.h`（对外契约）　`runtime/src/jm_native.c`（登记与分派）
> 版本：`JM_NATIVE_ABI_VERSION = 1`　更新时间：2026-11-09

---

## 1. 为什么先定 ABI

砾的硬件能力（`引脚.写`、`定时器.延时`、`adc.读`）不是运行时自带的内建，而是**由板级 C 模块提供**。这条边界一旦不确定，后面三件事都会变形：

- **H4 打包**：包里要写明「依赖哪个 native 表、版本多少」，锁文件才能还原出同一套符号；
- **H6.2 Arduino 桥接**：`setup()` 里只调一次 `jm_run`，外设驱动以 native 函数的形式接进来；
- **JM7 硬件绑定**：同一份 `.jsh` 在主机端口和 F103 上必须表现一致，差别只允许在 native 层。

所以先把签名、值读写、错误传播、可重入与中断规则钉死，再往表里填函数。

## 2. 分层与边界

```
砾源码 .jsh ──micc──▶ .jmb（只有名字，没有函数地址）
                          │
                          ▼
        jm_run：读名字表 → 内建(0..63) / 原生(64..127) 绑定到全局
                          │
                 ┌────────┴─────────┐
                 ▼                  ▼
        runtime（C99，可移植）   native 表（板级模块，可由第三方包提供）
        值/堆/VM/错误               GPIO / ADC / 定时器 / 外设库
```

三条硬边界：

1. **`.jmb` 里只放名字**，不存函数地址、不存 ABI 序号。绑定发生在 `jm_run` 时，找不到就是 `E004 名字未定义`。
2. **native 层不碰 VM 内部**：不解析值标签、不直接读写 `JmState`，只走 `jm_native.h` 里的函数。
3. **native 层不链进宿主工具链**：它是固件的一部分，随 `.jmb` 一起发布的是「包 + native 模块」，不是语言卡。

## 3. 登记与绑定

```c
typedef int (*JmNativeFn)(JmStateRef st, const JmValue *args, uint8_t nargs,
                          JmValue *out);

typedef struct {
    const char *name;
    JmNativeFn fn;
    uint8_t min_args;
    uint8_t max_args;
    uint8_t flags;     /* 保留，v1 必须为 0 */
    uint8_t reserved;  /* 保留，v1 必须为 0 */
} JmNativeEntry;

int jm_native_register(const JmNativeEntry *entries, uint8_t count);
```

规则：

| 规则 | 说明 |
|---|---|
| 登记时机 | `jm_run` 之前，任意次；通常放在板级初始化里，比 `jm_run` 早一行 |
| 容量 | 最多 8 张表、共 64 个表项（`JM_NATIVE_MAX_TABLES` / `JM_NATIVE_MAX_ENTRIES`） |
| 重名 | 视为登记失败（返回 `-1`），不做「后者覆盖」；名字冲突属于打包错误 |
| 保留位 | `flags`/`reserved` 非 0 → 登记失败。这是给未来 ISR 直调留的位置，现在不猜 |
| 生命周期 | 表必须是静态存储期（`static const`），运行时不复制表项 |
| 未绑定 | 名字在 `.jmb` 里但没人绑 → 与普通未定义名字同一条错误路径 |

绑定顺序：先内建（`打印`、`文本`…10 个），再原生表。原生表**不得**与内建重名。

## 4. 参数传递

| 项 | 约定 |
|---|---|
| 顺序 | 源码实参自左向右，`args[0]` 是第一个实参 |
| 个数 | `nargs ∈ [min_args, max_args]`，运行时在调 `fn` 之前检查；越界报 `E012` |
| 上限 | 单次最多 8 个（`JM_NATIVE_MAX_ARGS`）；更多的参数应由编译器侧拦下 |
| 所有权 | **调用期间借用**。不得保存 `args` 指针；要跨调用保存必须先 `jm_value_retain`，并在自己销毁时 `jm_value_release`（见下） |
| 类型 | 不做隐式转换。要整数就 `jm_value_to_int`，失败按 `JM_NE_TYPE` 报错 |
| 缺省 | 可选参数用 `min_args` 表达，native 内部按 `nargs` 分支；**没有默认值机制** |

`args` 指向 VM 值栈上的连续区域，返回后即失效。规则只有一条：**借用期内不保存 `args` 指针；要带走就 retain，并在自己销毁时 release**。例如缓存最后一次读数：`jm_value_retain(args[0])` 覆盖旧缓存，覆盖前先 `jm_value_release(旧值)`。未 retain 就跨调用保存，是未定义行为。

## 5. 返回值

| 项 | 约定 |
|---|---|
| 出口 | `*out`，成功时必须写；失败时**不保证**有值，运行时会丢弃 |
| 构造 | 只用 `jm_value_int` / `jm_value_bool` / `jm_value_nil` / `jm_value_make_text` |
| 整数范围 | ±268,435,455（29 位）。超范围的 `jm_value_int` 返回 `nil` —— 调用方先做范围检查并报 `JM_NE_PARAM` |
| 文本 | `jm_value_make_text` 新建，引用计数 1，**所有权交给运行时**，native 不要自己释放 |
| 借用文本 | `jm_value_text` 得到的指针只在本次调用期间有效；出参请新建 |
| 返回对象/容器 | v1 不支持。native 只能产出 int/bool/nil/text；容器由运行时构造 |

内存记账：native 里每次分配都算在同一个静态堆上（固件 `JM_HEAP_SIZE=6144`）。一个 native 反复分配而不产生可回收值，会直接导致 `E017 堆内存耗尽`——这是设计约束，不是 bug。

## 6. 错误传播

```c
return jm_native_fail(st, JM_NE_PARAM, "引脚号越界");
```

| 错误码 | 值 | 含义 |
|---|---|---|
| `JM_NE_PARAM` | 30 | 参数取值非法（越界、通道不存在） |
| `JM_NE_TYPE` | 31 | 参数类型不符（要整数给了文本） |
| `JM_NE_HW` | 32 | 硬件操作失败（总线无响应、外设未就绪） |
| `JM_NE_STATE` | 33 | 当前状态不允许（未初始化、已在用、重复启动） |
| `JM_NE_NOMEM` | 34 | 分配失败 |

规则：

1. `fn` 返回 0 = 成功；返回任何非 0 = 失败，**且必须已经 `jm_native_fail`**。
2. 返回非 0 却没报错 → 运行时补一条 `E033 原生函数状态错误`，便于抓漏（不会静默）。
3. 错误是**终止性**的：VM 停止，`jm_run` 返回 -1，`jm_last_error()` 给出 `错误[E0xx] 文案：detail`。
   从 JM13 起语言有 `抛出` / `尝试` / `捕获`，但这些 native 错误**不可被 `捕获` 拦截**：
   `E030` / `E031` / `E033` 与 VM 故障同级，直接终止程序。
4. native 不要自己 `jm_port_write` 报错信息；错误统一走错误码 + detail，由运行时排版。
5. ABI v2 预留 `jm_native_throw`（native 主动抛出可捕获的值）仅作为将来项记录，v1 不实现，
   所以现在 native 没有任何「可恢复错误」的表达能力。
6. detail 是静态字符串（或调用期间有效），运行时不复制。

## 7. 可重入与中断安全

### 7.1 线程模型

- 一个 `JmState` 只允许**一个线程**进入 `jm_run`。VM 不是可重入解释器。
- native 函数在「持有 VM 的那个线程」里同步执行，因此：
  - 可以调用其他 `jm_value_*` / `jm_native_fail`（它们只碰当前状态）；
  - **不得**递归调用 `jm_run`；
  - **不得**跨线程共享同一个 `JmState`。
- native 自身的可重入性由它自己负责：若同一张表被两个 VM 实例共用（主机端口多进程不会，固件里只有一份 `jm_state`），native 里不得有跨实例的 `static` 可变状态；有的话要按实例隔离或加锁。

### 7.2 中断

**v1 明确禁止在中断里调用 native 函数**，理由是三条同时成立：

1. native 可能分配（静态堆没有临界区保护）；
2. native 可能访问外设总线，耗时不可预算；
3. VM 的值栈/帧栈是单线程结构，ISR 里调用会破坏它。

中断里的正确做法（已有内核 API）：

```c
/* ISR 里只做最小动作：投递事件 */
jmk_sem_post_from_isr(&g_evt_sem);
jmk_queue_send_from_isr(&g_log_q, &ev, 0);
```

然后由承载 VM 的任务在 native 里 `jmk_sem_wait` / `jmk_queue_recv` 取事件、转成砾值返回。**ISR → 内核对象 → 任务 → native** 这条链是唯一允许的跨界方式。

JM7 的 `f103_exti` 表就是按这条链落地的，可以当作样板：砾侧只调用 `中断绑定` / `中断触发` / `中断计数` / `中断解除`（全部在任务上下文）；真正的中断服务函数在端口层 `EXTI_IRQHandler` / `EXTI9_5_IRQHandler` / `EXTI15_10_IRQHandler`（按线组分工），它们清本组挂起位、计数，然后回调板级 `irq_post_from_isr`，后者只执行一次 `jmk_queue_send_from_isr`。**中断里没有一行字节码、没有一次 VM 调用、也没有进 native 表**，所以 ABI v1 的「ISR 不得直调 native」没有被绕开。

`flags` 位是给 ABI v2 预留的：若将来真需要 ISR 直调，会新增 `JM_NATIVE_ISR_SAFE` 与独立的 ISR 入口，且只允许「无分配、无阻塞、无 VM 栈操作」的函数。现在填任何非 0 值都会登记失败。

### 7.3 阻塞

native 可以调 `jmk_*` 阻塞 API（等信号量、收队列），代价是**阻塞承载 VM 的那个任务**。契约上允许，因为固件里 VM 就属于某一个任务（`log`/`main`），没有第二个任务同时在跑同一个 VM。若以后要做「VM 被抢占式调度切片」，这条必须重谈。

## 8. 与打包（H4）的关系

- `砾包.toml` 里 native 依赖写成「表名 + ABI 版本」，例如：

  ```toml
  [native.f103]
  table = "f103_gpio"
  abi = 1
  ```

- 锁文件（`.砾/锁.toml`）只记录 `name / version / source / hash`，**没有 `abi` 字段**；ABI 一致性由 `micc` 在**编译期**校验（`compiler/src/pack.rs` 的 `check_native`，不一致报 `E129`），`micc install` 不校验 ABI。所以它既不是「安装时拒绝」，也不会拖到运行期报 `E004`。
- **不升版本的情形**：只往表里加函数、改实现。**必须升版本的情形**：改 `JmNativeFn` 签名、改值编码、改错误码含义、改参数所有权约定。
- 升版本要同时更新语言卡的 `native_abi_version`（`spec/langcard.json`，由 `jm_native.h` 的 `JM_NATIVE_ABI_VERSION` 自动渲染），二者不能各走各的。

## 11. 已落地的原生表：`f103_board` / `f103_adc` / `f103_timer` / `ipc_queue` / `ipc_sem` / `f103_exti` / `f103_bus`

代码：[f103_native.c](../firmware/stm32f103/f103_native.c)（板级七张表）、[jm_host_native.c](../runtime/port/host/jm_host_native.c)（主机六张表）　表头生成物：[runtime/include/jm_native_table.h](../runtime/include/jm_native_table.h)　登记点：[main.c](../firmware/stm32f103/main.c)（调度器启动前，依次登记七张表）

砾侧调用前必须写对应的 `导入 引脚` / `导入 ADC` / `导入 定时器` / `导入 队列` / `导入 信号量` / `导入 外部中断` / `导入 总线`；名字与参数个数在编译期校验（见 §12）。`导入 任务` 不是原生表（见 §11.4）。表项的名字、参数个数与 C 函数名由 `compiler/src/native_spec.rs` 生成，C 侧不再手写。七张表共 **32 项**（5 + 2 + 6 + 5 + 3 + 4 + 7），未超过 ABI v1 的「8 张表 / 64 项」上限（余 1 张表 / 32 项）。2026-11-08 新增 `ipc_queue.队列销毁`；2026-11-09（N10）`f103_bus` 并入 SPI 三项；`.jmb` 只存名字、id 是运行期内部约定，故两轮都不需要升 ABI。

| 名字 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `引脚写` | `(引脚, 电平)` | 无 | 引脚编码 `0–47`（0–15=PA0–PA15，16–31=PB0–PB15，32–47=PC0–PC15）；电平 `0/1`。首次写会把该脚配成推挽输出 2 MHz。**PC13 低电平点亮**，所以 `引脚写(13, 0)` 是亮 |
| `引脚读` | `(引脚)` | 整数 | 读该脚输入寄存器（0/1），引脚编码 `0–47`；不改引脚模式：本程序写成输出时读到驱动电平，未配置时读到悬空/外部电平 |
| `引脚翻转` | `(引脚)` | 无 | 按最后写入的电平取反（从未写过按 0），并配成推挽输出；引脚编码 `0–47` |
| `串口写` | `(文本)` | 无 | 直接写 USART1（115200 8N1），不换行、不加前缀 |
| `等待毫秒` | `(毫秒)` | 无 | 忙等 0–60000 ms；SysTick 中断仍在跑，调度器不参与 |

几点说明：

- 写了 `导入 引脚` 之后，名字拼错与参数个数不符在**编译期**就报 `E115`；没导入就调用报 `E113`，不会等到运行时 `E004`。运行时仍保留 `E004` 与 `E012` 作为兜底。
- 引脚越界报 `E030`；电平不是 0/1 报 `E030`；`串口写` 收到非文本报 `E031`。
- **任意引脚（2026-11-09 扩容，N22 前置）**：`引脚写/读/翻转` 从只认 PC13 扩到 **0–47**。板上实测（PB0 = 16 自读回）：`引脚写(16,1)` → `引脚读(16)=1`、`引脚翻转(16)` → `0`、`引脚写(16,0)` → `0`，PC13 亮灭不变；夹具 [examples/引脚回环.jsh](../examples/引脚回环.jsh) + [tests/expected/引脚回环.txt](../tests/expected/引脚回环.txt)，日志 `build/uart/n22-gpio.log`；代价 **+40 B Flash / +48 B RAM**（`g_pin_out[48]`）。读不改引脚模式，也没有内建上拉配置：外部输入要自己保证电平。主机替身同步补齐了这 5 项（写记电平、读回值、串口写打到 stdout、等待毫秒真睡），`test.ps1` **29/29**。
- 这些函数**不能进 ISR**（v1 通则）；需要中断驱动的外设，走 `ISR → jmk 对象 → 任务 → native`。
- 示例：[examples/board/点灯.jsh](../examples/board/点灯.jsh)（首行 `导入 引脚`），构建命令：

  ```powershell
  .\tools\build-firmware.ps1 -Example "board\点灯"
  ```

主机侧验证方式：用同名替身表（同 5 个名字、不碰硬件）跑同一份 `app.jmb`，可确认名字绑定与调用顺序，无需上板。编译期检查不依赖硬件：`tools/test-native-import.ps1` 只编不跑。

### 11.1 串口抓取：一条命令

接线：**PA9 → CH340 的 RXD，PA10 → CH340 的 TXD，GND 共地**（只用 TX/RX/GND，不要靠板子给 CH340 供电）。

```powershell
.\tools\capture-serial.ps1                                   # 默认 COM3 / 115200 / 60 秒
.\tools\capture-serial.ps1 -Port COM5 -Seconds 120 -Out .\build\uart\run1.log
```

- 参数：`-Port`（默认 `COM3`）、`-Baud`（默认 `115200`，8N1 固定）、`-Seconds`（默认 60）、`-Out`（默认 `build\uart\uart-<时间戳>.log`）。
- 顺序固定：**脚本先打开端口并开始录制，屏幕上出现「现在可以按复位键」之后**，你再按 RST，启动段不会漏。
- `DTR` / `RTS` 强制关闭，避免部分 USB 转串口把复位脚拉低造成反复重启。
- 落盘是原始字节（UTF-8，保留固件的 `\r\n`），编辑器可直接打开；收 0 字节时退出码 2，并提示检查 TX/RX 是否接反。

上板核对清单（`examples/board/点灯.jsh`）：`[原生] 板级函数表已登记：f103_board, f103_adc, f103_timer, task` → `[内核] 启动调度器…` → 4 轮 `LED 亮/灭`（各 400 ms）→ `翻转后，引脚读 = 0` → `板级示例结束` → `[砾] 程序正常结束` → 每 200 ms 一行 `[同步] 收到 seq=N`。

> JM8 起，砾程序在调度器启动后作为 `vm` 任务（优先 2，栈 1024 B）运行，所以「启动调度器」这一行出现在砾输出之前；`等待毫秒` 仍是忙等，`任务.延时` 才会真正让出。

### 11.2 ADC 表：`f103_adc`

代码：`port_adc_init` / `port_adc_read`（[stm32f103_port.c](../firmware/stm32f103/stm32f103_port.c)）＋ `n_adc_init` / `n_adc_read`（[f103_native.c](../firmware/stm32f103/f103_native.c)）。砾侧必须先写 `导入 ADC`。

| 名字 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `ADC初始化` | `()` | 无 | 打开 ADC1 时钟（PCLK2 / 6 = 12 MHz），PA0–PA7 设为模拟输入，上电并执行 RSTCAL + CAL 校准 |
| `ADC读` | `(通道)` | 整数 0–4095 | 对通道 0–7 做一次单次转换；通道号越界报 `E030`，未初始化报 `E033` |

硬件约定：

- 通道 `0..7` 一一对应 **PA0..PA7**，12 位分辨率，参考电压为 VDDA（3.3 V）。换算：整数写法 `电压 ≈ 原始值 × 3300 // 4095`（mV）；小数写法 `原始值 / 4095.0 × 3300`（先除后乘，避免中间量超过 Q12 值域 ±524288）。`ADC读` 返回整数，与小数混算时自动提升为 Q12。
- 输入电压必须在 **0–3.3 V** 之间，且与板子共地；超压会损坏引脚。高阻信号源建议外加运放跟随。
- 采样时间设为 239.5 个 ADC 周期，单次转换约 20 µs 量级；转换是阻塞的，不进 ISR。
- `ADC初始化` 会把 PA0–PA7 全部切成模拟输入，若同工程还要把其中某脚当 GPIO 用，需自行改回。

接线（读 PA0）：

```
信号源 + ── PA0（ADC1_IN0）
信号源 − ── GND（必须共地）
0 V   → 原始值约 0
3.3 V → 原始值约 4095
```

示例：[examples/board/ADC采样.jsh](../examples/board/ADC采样.jsh)，源码写的是「名义每 500 ms 读一次 PA0」，打印原始值与估算电压。**注意**：该示例上板验证时跑的是旧固件，`定时器延时(500)` 实际只有约 45 ms（+串口打印约 5 ms → 约 50 ms 一次），且日志里的 `定时器计数` 是 TIM2 计数值、不是毫秒；ADC 读数本身有效，但「每 500 ms 采样」的说法不成立，详见 §11.3：

```powershell
.\tools\build-firmware.ps1 -Example "board\ADC采样"
```

### 11.3 定时器表：`f103_timer`

代码：`port_timer_init` / `port_timer_delay_ms` / `port_timer_count`（[stm32f103_port.c](../firmware/stm32f103/stm32f103_port.c)）＋ `n_timer_*`（[f103_native.c](../firmware/stm32f103/f103_native.c)）。砾侧必须先写 `导入 定时器`。

| 名字 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `定时器初始化` | `()` | 无 | 置毫秒基准就绪标志（时基是 SysTick 1 ms 中断累加的 `g_ms`）；同时把 TIM2 配成 1 MHz 自由运行（`PSC = 71`，`ARR = 0xFFFF`） |
| `定时器延时` | `(毫秒)` | 无 | 按 `g_ms` 毫秒计数忙等 0–60000 ms；范围越界报 `E030`，未初始化报 `E033` |
| `定时器计数` | `()` | 整数 0–65535 | 读 `g_ms` 的低 16 位（1 ms 计数，约 65.5 秒回绕） |
| `PWM启动` | `(引脚, 频率赫兹, 占空比千分比)` | 无 | TIM4 PWM：引脚 22–25 = PB6–PB9 = CH1–CH4；频率 1–10000 Hz，占空比 0–1000；越界报 `E030` |
| `PWM占空比` | `(千分比)` | 无 | 运行中改占空比 0–1000；不改频率；越界 `E030`，未启动 `E033` |
| `PWM停止` | `()` | 无 | 关通道并把引脚拉低回普通输出；未启动报 `E033` |

时钟与引脚影响：

- **毫秒基准是 SysTick，不是 TIM2**（2026-11-08 修正）。`SysTick_Handler` 每 1 ms 给 `g_ms` 加一，`port_uptime_ms()` 返回它；`定时器初始化 / 延时 / 计数` 与 `等待毫秒` 全部按这个时基算。
- 修正前的缺陷：`PSC = 系统时钟 / 1000 − 1` 在 72 MHz 下算出 `71999`，写进 16 位 PSC 只剩 `6463`，TIM2 实际约 **11.138 kHz**（1 计数 ≈ 89.8 µs），名义「毫秒」一直偏快约 11 倍；`定时器延时(800)` 实际只有约 72 ms。SWD 读回 `TIM2_PSC = 0x193F`(6463) 是直接证据。现已把 TIM2 改成 `PSC = 71`（72 MHz / 72 = 1 MHz）自由运行，毫秒改由 SysTick 提供。
- TIM2 只使用计数器，不占用任何 GPIO，也不改 PA0–PA7 的模拟配置；可与 ADC 同时使用。
- `g_ms` 是 32 位，`定时器计数` 只取低 16 位，所以对外仍按 65.536 s 回绕；`毫秒差` 用 65536 补绕。单次延时上限 60000 ms，避免和回绕周期贴得太近。

**TIM2 缺陷波及的历史数据（2026-11-08 逐条复核）**：

| 历史测量 / 结论 | 走的哪条时钟 | 是否可信 |
|---|---|---|
| `定时器延时(N)` 的实际等待（旧固件） | TIM2 计数（PSC 截断后 11.138 kHz） | **不可信**。实际 ≈ N × 89.8 µs：`(800)`≈72 ms、`(500)`≈45 ms、`(20)`≈1.8 ms。现已改 SysTick，重新可用 |
| `定时器计数()` 的打印值（旧固件） | TIM2 16 位计数 | **不是毫秒**。1 计数 = 89.8 µs；`docs/verification/` 里 ADC 日志的 536/1092/1649/2206 是计数（约 48/98/148/198 ms），不是 0.5/1/1.5/2 秒 |
| ADC 上板记录「每 500 ms 读一次」 | 旧 `定时器延时(500)` | **不成立**：实际约 45 ms 一次（加串口打印约 50 ms）。ADC 读数有效，采样间隔表述作废 |
| OLED 屏上 `毫秒差` 显示（旧固件） | TIM2 计数当毫秒 | **不可信**，被放大约 11.138 倍；新固件已是真毫秒 |
| PWM 呼吸灯的呼吸周期 | 旧 `定时器延时(20)` | **不可信**：每步约 1.8 ms，整轮约 0.15 s（设计意图约 1.7 s）。PWM 频率本身不受影响（TIM4，见下） |
| `等待毫秒(N)`（`f103_board`） | `port_delay_ms` → 忙等 `g_ms`（SysTick） | **有效**，一直是真正的 N ms |
| `任务.延时(N)` / `jmk_delay` | `jmk_tick_count` ← `jmk_tick()` ← `SysTick_Handler`（`jmk.c:662`） | **有效**，SysTick 1 ms。「延时 200 ms、总耗时 611 ms」是主机侧真毫秒，与 TIM2 无关 |
| `耗时=NNN ms`（`main.c:269,305`） | `jmk_ticks()` ← `jmk_tick_count` ← `SysTick_Handler` | **有效**，与 `jmk_delay` 同一条 SysTick 链，不经 TIM2 |
| `port_uptime_ms()`（含 OLED 诊断插桩） | `g_ms` ← `SysTick_Handler` | **有效**。`git show 50fe03c:firmware/stm32f103/stm32f103_port.c` 可见修复前它就是 `return g_ms`，从来不经过 TIM2 |
| 「TIM2 1 kHz 已上板验证」 | — | **结论作废**：寄存器实读 `TIM2_PSC = 0x193F`(6463)，不是 71999 |

PWM 实现（2026-11-08 并入本表，不加表、不升 ABI）：

- 用 **TIM4**（APB1，`RCC_APB1ENR` bit 2）。毫秒基准已改回 SysTick，TIM2 只做 1 MHz 自由运行计数，两者都不用 TIM4。
- 常规档位 `ARR+1 = 1000` → 每周期 1000 个计数，`CCR` 直接写千分比：0 = 常低，1000 = 常高。
- `PSC` 粗分、`ARR` 细分：`PSC+1 = 系统时钟 / (频率 × 1000)`；只有低频端 PSC 装不下（`> 65536`，即 72 MHz 下的 1 Hz）才把 `ARR+1` 放大到能整除周期的因子（1 Hz → `PSC+1 = 64000`、`ARR+1 = 1125`），`CCR` 按 `占空比 × (ARR+1) / 1000` 换算，对外仍是千分比。72 MHz 下 1 kHz 仍是 `PSC = 71`、`ARR = 999`，与改前逐位一致。
- 引脚为 **PB6 / PB7 / PB8 / PB9（编码 22–25）**，默认映射，不需要 AFIO 重映射；起始配置为复用推挽 50 MHz。
- **PC13 不能 PWM**：它是纯 GPIO，没有定时器通道。板载 LED 只能整亮整灭。
- `PWM停止` 只关本通道（`CCxE=0`、`CEN=0`）并把该脚拉低，不影响 TIM2、也不影响其他通道。
- 示例：[examples/board/PWM呼吸灯.jsh](../examples/board/PWM呼吸灯.jsh)。接线：`PB6 → 220–330 Ω → LED → GND`（LED 长脚为正极）；板上可任选 22–25 之一，改示例第一个参数即可。

**PWM 有没有踩 TIM2 那个 16 位截断（2026-11-08 逐寄存器核对）**：

- **没有**。TIM4 是独立外设，`PSC`/`ARR` 都是 16 位，赋给它们的值本身不超过 65535。SWD 实读（`PWM启动(22, 1000, 0)` 运行中）：`TIM4_PSC = 0x47`(71)、`TIM4_ARR = 0x3E7`(999)、`TIM4_CCR1 = 0x352`(850)、`TIM4_CR1 = 1`(CEN)、`TIM4_CCMR1 = 0x68`、`TIM4_CCER = 1` → 72 000 000 / (72 × 1000) = **1000.00 Hz**，误差 0。TIM2 那种「算出来 71999、写进去只剩 6463」的静默截断在这里不可能发生（超界是显式 `-1` → `E032`，不是静默变值）。
- **1 Hz 曾经不可用，已改为 ARR 参与分频（2026-11-08 上板核对）**。旧实现 `PSC+1 = 72 000 000 / (1 × 1000) = 72000 > 65536` → `E032`，与「1–10000 Hz」的规格不符。现在 PSC 粗分后把 `ARR+1` 放大到 1125：SWD 实读 `TIM4_PSC = 0xF9FF`(63999)、`TIM4_ARR = 0x464`(1124)、`TIM4_CCR1 = 0x42C`(1068，对应约 950‰)，`CNT` 在改前读取时为 0x39B，72 000 000 / (64000 × 1125) = **1.000000 Hz**。这是**寄存器级证据**（读回 `PSC`/`ARR` 换算），不是示波器实测波形。
- **全频段复算**（72 MHz；寄存器档为实读，其余为整数分频公式；误差 = (实际 − 请求) / 请求）：

  | 请求 | `PSC+1` | `ARR+1` | 实际频率 | 误差 | 来源 |
  |---|---|---|---|---|---|
  | 1 Hz | 64000 | 1125 | **1.000000 Hz** | 0 | SWD 实读 `0xF9FF / 0x464` |
  | 10 Hz | 7200 | 1000 | 10.000000 Hz | 0 | 公式 |
  | 100 Hz | 720 | 1000 | 100.000 Hz | 0 | 公式 |
  | 1 kHz | 72 | 1000 | **1000.00 Hz** | 0 | SWD 实读 `0x47 / 0x3E7` |
  | 5 kHz | 14 | 1000 | 5142.86 Hz | **+2.86%** | 公式 |
  | 10 kHz | 7 | 1000 | 10285.7 Hz | **+2.86%** | 公式 |

  5k / 10k 的偏差来自 `PSC+1` 整数向下取整（`72e6 / (频率 × 1000)` 取整），**与 1 Hz 修复无关，改前就是这样**，照实保留、不抹平。1 kHz 及以下（1/10/100/1000 Hz）全部精确。
- **低频档的代价**：`ARR+1 = 1125` 时占空比分辨率是 1/1125（约 0.089%）而不是 1/1000；`CCR` 按 `占空比 × 1125 / 1000` 换算（50% → 562、95% → 1068），对外 API 仍是 0–1000‰，`.jsh` 不需要改。常规档位 `ARR+1` 仍是 1000，占空比分辨率不变。

### 11.4 语言层任务模块：`导入 任务`（JM8 续，不占原生表）

`任务` 模块不是 native 表：`创建 / 删除 / 让出 / 延时` 四个名字直接编译成操作码，由 VM 的绿色调度器执行。板级 [f103_native.c](../firmware/stm32f103/f103_native.c) 与主机 [jm_host_native.c](../runtime/port/host/jm_host_native.c) 里都**没有** `task` 表，`micc --emit-native-header` 生成的七张表里也没有它；实现见 `runtime/src/jm_vm.c` 的外层调度与 `compiler/src/vm_spec.rs`。

| 名字 | 参数 | 落成 | 说明 |
|---|---|---|---|
| `创建` | `(函数)` | `OP_TASK_CREATE`（38） | 创建一个无参子任务（根任务之外最多 3 个，第 4 次报 E038），返回整数句柄 |
| `删除` | `(句柄)` | `OP_TASK_KILL`（42） | 取消一个未在运行的任务（就绪 / 延时 / 等待中）：释放它的值栈与任务体，返回 `真`；句柄无效、已结束或指向当前任务返回 `假`。槽位与句柄暂不复用 |
| `让出` | `()` | `OP_TASK_YIELD`（39） | 有别的就绪任务就切走；没有就绪任务时立即返回 |
| `延时` | `(毫秒)` | `OP_TASK_DELAY`（40） | 睡够 0–60000 毫秒再继续，期间 CPU 交给其他任务 |

- 带超时的 `队列接收` / `队列发送` / `信号量等待` 也编译成等待操作码（见 §11.5、§11.6），不走 native 分派；不带超时的形式仍是普通原生调用。
- 固件里砾程序作为 `vm` 任务运行（优先 2，栈 1024 B，取自现有 3200 B 栈池），所以 `延时` 会真正切到 `led` / `log` 任务；`等待毫秒` / `定时器延时` 仍是忙等，不会让出。
- 示例：[examples/任务.jsh](../examples/任务.jsh)，主机上 `build\jmrun.exe build\任务.jmb` 输出 `任务开始 / 总 = 3 / 任务结束`。
- 板上实测（2026-11-08，`你好` 轮固件 27512 B 之后）：先用同一份 `examples/任务.jsh`（`延时(5)` ×3）烧录，串口输出与主机逐行一致；再用临时变体把延时改成 200 ms ×3 以观察让出，串口在 `任务开始` 与 `总 = 3` 之间插入 4 行 `[同步] 收到 seq=N`，程序耗时 611 ms（≈600 ms + 11 ms 开销），说明 `延时` 确实阻塞并让出了 CPU。同轮用 0xA5 哨兵扫描测得 **`vm` 栈峰值 368 B / 1024 B，余量 656 B**（`jmk_stack_used`）。
- `让出` 的独立证据（2026-11-08 补）：固件加 `-DJMK_YIELD_DEMO=1 -DJMK_IPC_DEMO=0` 编一份变体，建一个与 `vm` 同优先级（2）的 `peer` 任务，每轮打印后 `jmk_yield()`；配 `examples/让出.jsh`（循环里 `让出()`）。串口原文：

  ```
  让出：甲开始
  甲 0
  [让出] 乙 1
  甲 1
  [让出] 乙 2
  甲 2
  [让出] 乙 3
  甲 3
  [让出] 乙 4
  让出：甲结束
  ```

  甲/乙严格交替，说明 `让出()` 确实由 PendSV 切到了另一个任务；`.jsh` 结束后 `peer` 继续单独打印。该变体只用于取证，最终烧回默认构建（见 §11.5 上板记录）。
- 本轮没有做：删除任务、优先级、抢占切片；队列/信号量已做（见 §11.5、§11.6），仍没有变量查看与多断点；`让出` 的主机侧没有并发，只验证「不报错、不改变输出」。

### 11.5 队列表：`ipc_queue`（JM8 续）

代码：板级 [f103_native.c](../firmware/stm32f103/f103_native.c)（整数句柄 → 静态 `JmkQueue` 槽，缓冲 8 × 4 B）、主机 [jm_host_native.c](../runtime/port/host/jm_host_native.c)（单执行流环形缓冲）。砾侧先写 `导入 队列`。

| 名字 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `队列创建` | `(槽数)` | 整数句柄 | 槽数 1–8；句柄从 1 起。最多同时存在 3 个队列，用尽返回 `E034` |
| `队列发送` | `(句柄, 整数[, 超时毫秒])` | 真 / 假 | 队列满且等到超时返回 `假`；超时默认 0（不等待），范围 0–60000 |
| `队列接收` | `(句柄[, 超时毫秒])` | 整数 / 空 | 有数据返回整数，超时返回 `空`；超时默认 0 |
| `队列数量` | `(句柄)` | 整数 | 当前消息条数（调试用快照） |
| `队列销毁` | `(句柄)` | 真 / 假 | 释放队列控制块并返回 `真`；句柄无效或已销毁返回 `假`。正在等待该队列的任务按「未成功」返回（发送/接收按超时路径返回 `假`/`空`）；槽位缓冲归调用方，不随队列释放 |

- **句柄是整数，JMB 格式没有改动**：`.jmb` 里仍然只有名字和四个参数槽，句柄只是普通整数值。板级与主机都用「槽位号 + 1」编号，所以同一份 `.jsh` 打印出的句柄一致。销毁后槽位立即可复用，`队列创建` 会重新给回同一句柄。
- 板级直接调 `jmk_queue_init/send/recv/count/destroy`：等待按 JMK 优先级排队，只有任务能等；在非任务上下文调用返回 `E033`。主机侧没有别的执行流，等不到时睡满超时再返回 `假`/`空`，超时 0 立即返回，所以可见输出与板上逐字一致。
- 队列项固定为 32 位整数，不支持文本/结构体/借用指针；队列已支持销毁（`队列销毁`），信号量仍只创建不销毁。

### 11.7 外部中断表：`f103_exti`（JM7 收尾）

代码：端口层 [stm32f103_port.c](../firmware/stm32f103/stm32f103_port.c)（GPIO/EXTI/NVIC 与三个 ISR 入口）、板级 [f103_native.c](../firmware/stm32f103/f103_native.c)（ISR 回调与四个 native 函数）、主机 [jm_host_native.c](../runtime/port/host/jm_host_native.c)（软件模拟投递）。砾侧先写 `导入 外部中断`。

| 名字 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `中断绑定` | `(引脚, 队列句柄[, 边沿])` | 真 | 引脚 `0–47`：`0–15`=PA0–PA15，`16–31`=PB0–PB15，`32–47`=PC0–PC15；EXTI 线号 = 引脚 `% 16`。边沿 `0`=上升（默认）/`1`=下降/`2`=双沿 |
| `中断触发` | `(引脚)` | 真 / 假 | 软件触发该线一次；板上写 `EXTI_SWIER`，主机直接模拟投递；未绑定返回 `假` |
| `中断计数` | `(引脚)` | 整数 | 自绑定以来进入中断服务函数的次数 |
| `中断解除` | `(引脚)` | 真 | 关该线 `IMR` 与对应 NVIC 位、清挂起；同组还有别的线在用时只关本线。之后 `中断触发` 返回 `假` |

- **线号到中断号**：线 `0–4` = IRQ6–10（`EXTI_IRQHandler`），线 `5–9` = IRQ23（`EXTI9_5_IRQHandler`），线 `10–15` = IRQ40（`EXTI15_10_IRQHandler`）。启动文件向量表已补齐到 IRQ42（共 59 个向量字：16 个系统向量 + 43 个外设向量），三条 ISR 都在表内。
- **中断里不跑字节码**：三个 ISR 共用一个 `exti_serve(first, last)`：只读 `EXTI_PR`、写 1 清**本组**的位、计数，然后调用 `irq_post_from_isr`；后者只执行 `jmk_queue_send_from_isr(队列, &引脚号, 0)`。没有 VM 调用、没有 native 分派、没有分配，所以不存在「ISR 里重入 VM」的风险。
- **数据是事件，不是共享内存**：中断投进队列的载荷就是编码后的引脚号。`中断触发` 只写触发位并返回 `真`，不携带数据，因此任务收到的值只能来自中断服务函数——这条链路可以自证。
- **端口与线的一对多**：EXTI 的每条线同一时刻只能选一个端口，由 `AFIO_EXTICR1–4` 决定（0=PA、1=PB、2=PC）。把 PB5 绑到线 5 后再绑 PC5，后者会先解绑前者，因为二者共用线 5。绑定时按端口写 `IOPxEN` 时钟、`CRL/CRH` 下拉输入（nibble `0x8`）、清 `ODR` 位。
- **真实触发源**：板上没有用户按键（PC13 是 LED 输出，接的是限流电阻），所以本轮到板证据用的是 `EXTI_SWIER` 软件触发——它和外部边沿走的是同一条 `EXTI → NVIC → ISR` 路径，不是绕过中断直接调用。PA0–PA4 同时被配成下拉输入，把 PA0 接 3V3 就能拿到真实上升沿，同一份 `.jsh` 不用改。
- 引脚会被改成下拉输入；**不要和 `引脚` 表的 PC13 输出、ADC 的 PA0–PA7 模拟输入同时抢同一脚**。PA9/PA10 是串口，本表不含。
- 每路中断独立计数，`3 路对象槽` 的队列上限仍然适用：中断投递到已满队列时会丢事件（计数值仍然增加），所以检查队列数量与计数是否对得上，能看出丢没丢。
- 示例：[examples/外部中断.jsh](../examples/外部中断.jsh)（PA0/PA1 各触发两次、按序收齐、解除后不再触发）；[examples/外部中断_扩展线.jsh](../examples/外部中断_扩展线.jsh)（PB5=21、PC13=45，覆盖 IRQ23 与 IRQ40 两条线）；基准输出 [tests/expected/外部中断.txt](../tests/expected/外部中断.txt)、[tests/expected/外部中断_扩展线.txt](../tests/expected/外部中断_扩展线.txt)。

上板核对（`-Example 外部中断`，2026-11-08）：`[原生] 板级函数表已登记：f103_board, f103_adc, f103_timer, task, ipc_queue, ipc_sem, f103_exti` → 18 行输出与主机逐行一致，其中 `收到 = 0 / 1 / 0 / 1`、`PA0 计数 = 2`、`PA1 计数 = 2`、`解除后触发 PA1 = 假`；`vm` 栈峰值 368 B / 1024 B；无 HardFault。

真实外部边沿上板核对（`-Example "board\PA0边沿"`，2026-11-08，COM4 抓包 101 127 B）：PA0 处于下拉低电平期间计数严格为 0（`等待中 10 秒，计数 = 0`、`等待中 20 秒，计数 = 0`），接线后出现 `边沿 = 0 计数 = 2 → 235 → 1167 → … → 5995`，40 秒后完全静默（`等待中 40 / 80 / 290 秒，计数 = 8361`）。因为该示例不含 `中断触发`，这些事件只能来自 `EXTI_IRQHandler`，即真实引脚边沿。**但一次手接线产生了 8361 次边沿（约 2–4 kHz）**：内部下拉约 40 kΩ、长跳线悬空时更易抖振，说明这是接触噪声而不是一条干净边沿；要单条边沿证据需用短硬跳线，或在 PA0 对 GND 加 100 nF 后再测。该轮固件 FLASH 31 932 B（诊断开）/ 31 764 B（`-DJM_STACK_DIAG=0`），RAM 均 14 940 B。

### 11.8 总线表：`f103_bus`（I2C + SPI，JM7 收尾 / N10 2026-11-09）

代码：端口层 `port_i2c_*` / `port_spi_*`（[stm32f103_port.c](../firmware/stm32f103/stm32f103_port.c)）＋ `n_i2c_*` / `n_spi_*`（[f103_native.c](../firmware/stm32f103/f103_native.c)）；主机替身 [jm_host_native.c](../runtime/port/host/jm_host_native.c)（`I2C探测` 只对 `0x3C` 返回真，`I2C写` 打印命令轨迹；`SPI收发` 回环、`SPI写块` 打印字节轨迹）。砾侧先写 `导入 总线`。

| 名字 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `I2C初始化` | `(SCL引脚, SDA引脚, 速率千赫兹)` | 真 / 假 | 引脚编码 `0–47`；速率 `10–400` kHz。**26/27（PB10/PB11）走硬件 I2C2**，返回 `真`；其它引脚组合走软件位翻转，返回 `假`；SCL 与 SDA 相同、引脚越界、速率越界报 `E030` |
| `I2C写` | `(设备地址, 控制字节, 数据字节)` | 无 | 地址 `0–127`，控制/数据字节 `0–255`；未初始化报 `E033`；从机无应答报 `E032` |
| `I2C写块` | `(设备地址, 控制字节, 数据1 … 数据5)` | 无 | 一次事务连续写 **1–5** 个数据字节（`JM_NATIVE_MAX_ARGS = 8`，3 个固定参数 + 5 个数据）；无应答报 `E032` |
| `I2C探测` | `(设备地址)` | 真 / 假 | 发地址后看 ACK；未初始化报 `E033` |
| `SPI初始化` | `(SCK引脚, MISO引脚, MOSI引脚, 分频)` | 真 / 假 | 引脚编码 `0–47`，三脚不能重复；分频只能是 `2/4/8/16/32/64/128/256`。**5/6/7（PA5/PA6/PA7）走硬件 SPI1**，返回 `真`；其它组合走软件位翻转，返回 `假`；引脚越界/重复、分频非法报 `E030`，初始化失败报 `E032` |
| `SPI收发` | `(数据字节)` | 整数 | 一次全双工交换，返回同时收到的字节（`0–255`）；数据越界报 `E030`；未初始化报 `E033`；总线超时报 `E032` |
| `SPI写块` | `(数据1 … 数据5)` | 无 | 连续发送 **1–5** 个字节并丢弃收回值；数据越界报 `E030`；未初始化报 `E033` |

- **硬件 I2C2**：base `0x40005800`，PB10 = SCL / PB11 = SDA 是默认映射，不需要 AFIO 重映射；两脚配成复用开漏 50 MHz。`RCC_APB1ENR_I2C2EN = 1<<22`。寄存器：`CR1`（PE/START/STOP/SWRST）、`CR2`（FREQ）、`DR`、`SR1`、`SR2`、`CCR`（bit15 = FS）、`TRISE`。
- **分频按 APB1 = 36 MHz 算**（72 MHz 主频、`PPRE1 = /2`）：
  - 标准模式：`CCR = 36000 / (2 × 100) = 180`、`TRISE = 37`；
  - 快速模式：`CCR = 36000 / (3 × 400) = 30`，写 `FS | 30 = 0x801E`，`TRISE = (36 × 3)/10 + 1 = 11`。
  - 若 HSE 缺席退回 HSI 8 MHz，APB1 = 8 MHz，`g_pclk1` 会按实际时钟重算上面两式，不会沿用 36 MHz 的常数。
- **软件位翻转是兜底通道**（几十 kHz，靠模块自带上拉），只在接线不是 PB10/PB11 时使用；硬件路径初始化失败不会自动回退到软件。
- **上拉必需**：I2C 是开漏，四针 OLED 模块一般自带 4.7 k。上拉缺失的表现就是扫描全无应答、`I2C探测` 恒假。
- **400 kHz 的稳定性边界**：本轮只在 `0x3C` 的 SSD1306（自带 4.7 k 上拉、短线）上连续刷新多轮，诊断计数随帧递增、无 NAK/卡死。这只是**一个模块 + 一种短线接线**的观察，没有做小时级长跑和长线/弱上拉测试（已做的 401 / 4001 帧定帧数长跑见 §11.10，最长一轮 8.7 分钟）；上拉不足或线缆较长时应把 `I2C初始化` 第三个参数退回 `100`，`.jsh` 其余部分不用改。
- 每次 `I2C写块` 是一次独立 START…STOP 事务；`.jsh` 侧按 5 字节一段连续推页，段间不插其它命令。
- **硬件 SPI1**：base `0x40013000`，PA5 = SCK / PA6 = MISO / PA7 = MOSI 是默认映射，不需要 AFIO 重映射；SCK/MOSI 配复用推挽 50 MHz，MISO 配浮空输入。`RCC_APB2ENR_SPI1EN = 1<<12`。`CR1 = MSTR | SSM | SSI | SPE | BR`（主机、NSS 软件、模式 0、MSB 先行）；`BR = log2(分频) − 1`，PCLK2 = 72 MHz 时分频 2 即 36 MHz。发送：等 `TXE` → 写 `DR` → 等 `RXNE` → 读 `DR`（两次等待都有超时）。
- **软件位翻转是 SPI 的兜底通道**：只有 5/6/7 走硬件；其它引脚组合 SCK/MOSI 推挽输出、MISO 浮空输入，模式 0 逐位翻转，延时常数随分频放大（几十 kHz 量级）。硬件路径初始化失败不会自动回退。
- **主机替身的行为**：`SPI收发` 做回环（返回发出的字节），`SPI写块` 打印 `[SPI] 写 N 字节：0x..`，`SPI初始化` 打印通道与分频；夹具 [examples/SPI回环.jsh](../examples/SPI回环.jsh) + [tests/expected/SPI回环.txt](../tests/expected/SPI回环.txt)。
- **上板（2026-11-09，N10 补验）**：PA6–PA7 短接做回环，板上 `SPI初始化` 返回 `真`（硬件 SPI1），`SPI收发(165 / 90 / 255 / 0)` 全部原样收回（`回环： 165 90 255 0`）；该固件 43 656 / 17 356、耗时 13 ms，日志 `build/uart/n10-spi-loop.log`。这证明硬件 SPI1 主机、模式 0、MSB 先行与 MISO 采样在短线回环下正确。
- **仍未覆盖**：真实从机通信（片选、时序余量、长线）、软件位翻转的实际速率、以及 2 以外的分频档——回环只证明「发什么收什么」，不证明与具体传感器/Flash 兼容。**真实从机测试等第二块板到货后再做**（已登记为路径图 §10.2 的 N22）。开测前置缺口已补：`引脚` 表 2026-11-09 已从「只认 PC13」扩到 **0–47**，`引脚写(CS引脚, 0)` 可直接驱动片选（上板验证见 §11.1 引脚表）。
- 示例：[examples/board/OLED文字.jsh](../examples/board/OLED文字.jsh)（I2C）、[examples/SPI回环.jsh](../examples/SPI回环.jsh)（SPI 主机回环）。

### 11.9 OLED 上板：闪屏缺陷与修复（用户上屏确认）

**这是缺陷修复，不是「优化了刷新」**，记录如下：

- **缺陷现象**：第一版刷新循环每帧先调 `清屏()`，向 8 页 × 128 列写 `0x00`，整块显存先被打成黑，再重画文字。屏上表现为每帧一次整屏闪白，计数器每变一次就闪一次。
- **叠加因素**：当时 TIM2 的 `PSC = 71999` 写进 16 位寄存器只剩 `6463`（实际约 11.138 kHz），`定时器延时(800)` 实际只有约 72 ms，帧率比预期快约十倍，闪更明显（见 §11.3）。
- **修法**：改成页级双缓冲。`缓冲` 是 128 字节 RAM 列表（512 B 堆），每帧只在 RAM 里拼好一整页，再整页连续推给屏；**每帧不再发清屏命令**，只在开机 `首次清屏()` 写一次全 0；初始化序列也只在开机发一次。整帧 1024 字节列表需要 4 KB，RAM 余量只有 3.4 KB，放不下，所以按页缓冲而不是整帧缓冲。
- **提速**：I2C 从 100 kHz 提到 400 kHz，分频按 36 MHz 重算（见 §11.8）。
- **取证方式**：为排除 VM 空隙、只量总线，临时在 `port_i2c_write` / `i2c2_write` 前后插桩：用修正后的 **TIM2（1 MHz，1 计数 = 1 µs）取差**累加纯总线时间，按 50 ms 空闲切分突发；同一次运行另记 `g_ms`（SysTick 1 ms）作墙钟。SWD 用 **hotplug** 读回（OLED 长循环固件下可读；目标停止/睡眠时 hotplug 报 `DEV_TARGET_CMD_ERR`，只有此时才退回 `mode=normal`，而该模式每次连接软复位，读到的多是复位瞬间值）。取证完成后插桩已删除，最终固件不含诊断代码（`git diff` 为空）。
- **实测（板级，2026-11-08，页缓冲 + 只推第 6 页；同一份代码只换速率档）**：

  | 速率档 | 每次数据字节 | 纯总线（TIM2 µs 计时） | 墙钟（SysTick `g_ms`） |
  |---|---|---|---|
  | 400 kHz（`CCR=0x801E`，`TRISE=0x0B`） | 128（1 页） | **4.11 ms**（`busy_us=0x1012`） | 6 ms |
  | 400 kHz | 1536（12 页连续突发） | **49.35 ms**（`max_busy_us=0xC0C7`，合每页 4.11 ms） | 227 ms |
  | 100 kHz（`CCR=0xB4`，`TRISE=0x25`） | 128（1 页） | **16.36 ms**（`busy_us=0x3FE9`） | 18 ms |
  | 100 kHz | 1536（12 页连续突发） | **196.3 ms**（`busy_us=0x2FEE8`） | 381 ms |

- **400 kHz 是否真的跑在 400 kHz**：三条独立证据。① 寄存器实读 `I2C2_CR2 = 0x24`（FREQ = 36，与 APB1 = 36 MHz 一致）、`CCR = 0x801E`（FS | 30）、`TRISE = 0x0B` → 36 MHz / (3 × 30) = 400 kHz；② 同一份代码 128 B 单页：100 kHz 16.36 ms → 400 kHz 4.11 ms，比值 **3.98 倍**，与 4 倍理论吻合（不是「只快一点」，也不是 3.5 倍）；③ 位时间核对：一页 128 B 拆成 25 次 5 字节 + 1 次 3 字节事务，400 kHz 的理论位时间约 4.2–4.4 ms，实测 4.11 ms 落在这个窗口——若实际只是 100 kHz，这个窗口必须 ≥16 ms。**要判断 400 kHz 是否成立，看这三个数，不要看整屏折算值。**
- **旧数 601 / 341 ms 的口径（重要）**：它们是**真毫秒**——当时也用 `port_uptime_ms` → `g_ms` → SysTick，不是 TIM2 计数；但量的是已删掉的「逐帧清屏 + 重画、100 kHz」旧代码路径，且含 VM 空隙。同口径新代码（100 kHz、1536 B 突发）是 **381 ms 墙钟 / 196.3 ms 纯总线**，所以**旧 601/341 不能与新数直接相减**，只能作为「旧路径确实慢」的定性记录保留。
- **旧表里的「整屏 1024 B = 84 ms」是推算，不是实测，本轮作废**：它是 6 ms（墙钟）× 14 页算出来的。**实测替代值（纯总线 / 墙钟双口径，见上表）**：1536 B 十二页突发 400 kHz = **49.35 ms 纯总线 / 227 ms 墙钟**；100 kHz = **196.3 ms 纯总线 / 381 ms 墙钟**。整屏 8 页按单页实测折算：400 kHz ≈ **32.9 ms 纯总线**、100 kHz ≈ **130.9 ms**（仍是折算，不是独立测量；要精确整屏数需另测一次 8 页突发）。

- **验收**：改后固件烧入板子，由用户上屏肉眼确认——**屏幕不再闪，计数器持续递增**。这是人眼验收，不是只凭日志推断。
- **「只传变化字节」没做**：当前已经是「只传变化页」（每帧 128 B，纯总线 **4.11 ms**、墙钟 6 ms）。再细到字节要逐列比较 RAM 与上次内容，`.jsh` 侧每帧多 128 次比较、还要再存一份 128 B 影子缓冲（RAM 已紧），收益最多把 4.11 ms 的纯总线降到 1 ms 量级，不值得。
- **体积（本示例）**：诊断开 FLASH **44 548 B**（67.97%）/ RAM **17 084 B**（83.42%）；诊断关（`-DJM_STACK_DIAG=0`）FLASH **44 376 B**、RAM **17 084 B**；RAM 余 **3 396 B**。相对 PWM 轮（38 084 / 37 916、RAM 17 068）是 FLASH **+6 464 / +6 460 B**、RAM **+16 B**。

### 11.10 OLED 长跑稳定性实测（401 / 4001 帧，2026-11-08）

- **观测方式**：COM4 串口逐帧一行 `帧 N 推页 X ms 累计 Y`，每帧另做一次 `I2C探测(0x3C)` 作为「屏幕仍在应答」的代理；汇总行输出实跑帧数、总耗时、单帧平均、推页平均/最大/最小、无应答数。录制用 `tools/capture-serial.ps1 -Port COM4 -Seconds 640 -Out <新文件>`，115200 8N1。
- **硬指标的读法**：① 帧序号严格 1→N 连续，说明主循环没有被卡住或复位重启（复位会让序号回到 1，日志里会出现第二段启动输出）；② `I2C` 失败在端口层直接报 `E032` 并终止 VM，所以「4001 行逐帧行 + 0 条错误行 + 正常结束汇总行」同时成立，等价于全程无 NAK、无超时、无终止；③ 推页耗时逐帧落在 7–8 ms，无离群值，说明总线没有被偶发拉长。
- **未覆盖（本表不替代）**：
  - **像素内容**：没有摄像头、SSD1306 GDDRAM 读回也未实现，所以「屏幕画出来的字符/位置是否正确」完全没测，只测到「通信持续正常 + 程序持续前进」。长跑期间屏幕显示由用户肉眼可看，但本轮没有逐帧记录图像。
  - **波形**：没有逻辑分析仪/示波器，SCL/SDA 的电平、上升沿、时钟占空比未观测；400 kHz 的成立依据仍是 §11.9 的三条寄存器/比值证据。
  - **时间分辨率**：`推页` 用 `定时器计数()`（SysTick 1 ms）取差，7 / 8 ms 是量化值，不是亚毫秒测量；单帧平均、总耗时同样以 1 ms 为最小粒度。
  - **长时间尺度**：最长单轮 521 561 ms（约 8.7 分钟），不是小时级；长线、弱上拉、多模块并联都未测。
  - **断电/热插拔**：未做掉电恢复与 I2C 线松动测试。
- **两轮作废数据的口径（不要再引用）**：
  1. 长测首版脚本漏写 `函数 扫描()` 定义（`扫描` 不是原生函数），运行即 `E004 名字未定义：扫描`，只打印两行启动文字，**没有产出任何帧数据**——作废原因是脚本缺陷，不是 I2C 故障；补上函数后才得到有效数据。
  2. 第一次 401 帧轮次的日志文件被 `capture-serial.ps1` 的**追加写**混入了上一支固件的常驻输出（开头是 `[同步] seq=273…`），帧行无法与旧内容分离，**整份日志作废**，改用新文件名重录。
  3. 第一次 4001 帧轮次录制窗口比程序结束早约 13 s，只抓到 3895 帧、没有结尾汇总行，**整轮作废**；随后给逐帧行加上 `累计` 字段并把窗口延长到 640 s 重跑，才得到上表的 4001 帧完整数据。

## 12. 编译期 `导入` 与单一事实来源

### 12.1 谁负责什么

| 阶段 | 负责方 | 做的事 | 失败表现 |
|---|---|---|---|
| 编译期 | `micc`（`compiler/src/native_spec.rs` + `codegen.rs`） | 校验 `导入 模块` 的模块名、函数名是否存在、是否已导入、参数个数是否落区间 | `E112` / `E113` / `E115`，退出码 1，不产出 `.jmb` |
| 运行期 | `runtime/src/jm_native.c` | 按名字把 `.jmb` 里的全局名绑定到已登记表项，再按 `min_args` / `max_args` 复核后分派 | `E004`（名字未定义）、`E012`（参数个数） |

关键点：**导入不改变字节码**。`.jmb` 里仍然只有名字、没有函数地址、也没有新的导入指令；`导入` 只决定编译器允许哪些名字出现。运行期仍走原来的「名字 → 表项」绑定，所以主机端口、F103 固件和将来的包安装都共用同一套分派路径。

### 12.2 为什么不会出现两份名字表漂移

1. **唯一事实来源**：模块名、表名、函数名、参数个数、C 函数名全部写在 [compiler/src/native_spec.rs](../compiler/src/native_spec.rs)。
2. **C 侧表是生成物**：`micc --emit-native-header` 生成 [runtime/include/jm_native_table.h](../runtime/include/jm_native_table.h)；板级 `f103_native.c` 展开 `F103_*_INIT` 与 `JM_TASK_TABLE_INIT`，主机 `jm_host_native.c` 展开同一份 `JM_TASK_TABLE_INIT`，两边都不手写名字表。
3. **构建期比对**：`micc --check-native` 在 `build.ps1` 与 `build-firmware.ps1` 的第 2 步比对入库头文件与规格，不一致直接失败。所以编译期接受的名字/参数个数，和运行期登记的名字/参数个数，来自同一次生成。
4. **文档同源**：语言卡的 `native_modules` 段也从这份规格生成，`micc --check-langcard` 再保证文档没落后。

### 12.3 编译期规则（v0）

- `导入 模块` 只能写在模块顶层；v0 有七个模块：
  - `引脚` → 原生表 `f103_board`（5 项）
  - `ADC` → 原生表 `f103_adc`（2 项）
  - `定时器` → 原生表 `f103_timer`（3 项）
  - `任务` → 不占原生表：`创建/删除/让出/延时` 编译成 `OP_TASK_*`（见 §11.4）
  - `队列` → 原生表 `ipc_queue`（5 项，板级与主机同名）
  - `信号量` → 原生表 `ipc_sem`（3 项，板级与主机同名）
  - `外部中断` → 原生表 `f103_exti`（4 项，板级与主机同名）
- 模块名不存在 → `E112`，提示当前可用模块。
- 没导入就调用原生名 → `E113`，提示「先写：导入 <模块>」。
- 已导入但参数个数不符 → `E115`；与导入模块里的名字只差一个字（如 `引脚写写`）也按拼错报 `E115`。
- 原生函数只能直接调用：不能当值使用，也不能用 `令` / `函数` / 赋值覆盖同名（`E115`）。
