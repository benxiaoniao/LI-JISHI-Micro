# 砾微内核（JMK）调度模型

面向 STM32F103C8T6（Cortex-M3，64 KB Flash / 20 KB RAM）的最小任务系统，目标是与后续的 `砾-RT` 层衔接，最终长成类 FreeRTOS 的内核。

## 一、调度模型

| 项目 | 选择 |
|---|---|
| 抢占方式 | **抢占式**（SysTick 驱动），任务无需主动让出 |
| 优先级 | 固定优先级 `0..3`，数字越大越优先；空闲任务固定 0 |
| 同优先级 | FIFO 轮转（就绪队列队尾入队、队头出队） |
| tick | 1 ms（`SysTick`，`JMK_TICK_HZ = 1000`） |
| 调度点 | SysTick 到期唤醒、`jmk_delay()` 阻塞、`jmk_yield()` 主动让出、创建更高优先级任务、删除当前任务 |
| 空闲任务 | 内核内置，最低优先级，循环 `WFI` 省电 |

**为什么选抢占式**：Cortex-M3 硬件原生支持 PSP/MSP 双栈与 PendSV，切换成本低且确定；抢占式能给出可预测的响应延迟，是 FreeRTOS 类内核的基础。协作式调度留给 JM8 的「砾层」（`让出`/`延时` 语义），两者可以并存：砾任务最终通过内核 API 落地为 C 任务。

## 二、任务状态机

```
FREE ──创建──▶ READY ──被选中──▶ RUNNING ──jmk_delay──▶ BLOCKED
                 ▲                   │                    │
                 └──── tick 到期 ────┘◀──── 唤醒 ◀─────────┘
                                    │
                         删除 ──▶ DEAD ──创建复用──▶ READY
```

- `FREE`：空槽位，可复用（任务槽 6 个）。
- `READY`：在对应优先级就绪队列里排队。
- `RUNNING`：当前任务，不在就绪队列中（被抢占时回队尾）。
- `BLOCKED`：`wake_tick` 到期后由 SysTick 放回就绪队列。
- `DEAD`：已删除，不再入队；槽位可被新任务复用。

## 三、临界区与中断优先级

- 临界区用 **PRIMASK 关中断**（`cpsid i` 前保存、`cpsie i` 后恢复），只包住就绪队列的链表操作，长度是几十条指令。
- 内核对象（就绪队列、TCB）只在「任务上下文 + SysTick」两处访问，二者通过 PRIMASK 互斥。
- `SysTick` 与 `PendSV` 的 NVIC 优先级都设为 **0xFF（最低）**，二者同优先级、不能互相抢占，避免上下文切换被 tick 打断。
- `SVC` 保持默认最高优先级，只用于「启动第一个任务」。

## 四、PendSV + SysTick 的用法

- 每个任务栈初始化时手工构造 **异常帧**（低→高：`R0 R1 R2 R3 R12 LR PC xPSR`，`xPSR = 0x01000000` 置 Thumb 位）+ **软件帧**（`R4..R11`），栈指针指向 `R4` 槽，栈顶 8 字节对齐。
- `jmk_start()`：建空闲任务 → 选最高优先级任务 → 写 `CONTROL.SPSEL = 1`（线程模式改用 PSP）→ `svc 0`。
- `SVC_Handler`：弹出 `R4..R11`、把 PSP 指向 `R0` 槽、`bx lr`（`EXC_RETURN = 0xFFFFFFFD`）完成首次进入任务。
- `PendSV_Handler`：`mrs r0, psp` → `stmdb r0!, {r4-r11}` 存软件帧 → 写回 `tcb->sp` → `bl jmk_schedule` → 取下一任务 `sp`、恢复 `R4..R11` → `bx lr`。异常帧由硬件弹出。
- 切换点全部延后到 PendSV：SysTick 只 `PENDSVSET`，保证不会在中断里做切换，中断延迟可控。
- 主栈（MSP）在启动后专供中断与异常使用，即 2 KB 主栈兼作 ISR 栈。

## 五、任务栈与内存分配

### 5.1 任务栈动态分配（`JMK_USE_STATIC_STACKS = 0`，默认）

| 项目 | 设计 |
|---|---|
| 栈来源 | 内核独立栈池 `jmk_stack_pool`（3200 B），**与砾运行时堆 `jm_heap`（6144 B）完全分离** |
| 分配粒度/对齐 | **8 字节**；每块块头 2 字（8 B），载荷天然 8 字节对齐 |
| 算法 | 地址升序空闲链 + **first-fit** + 前后邻合并（块头存 size，边界标记式） |
| 失败处理 | 池不足返回 `NULL` → `jmk_task_create_ex` 返回 **-1**，不占 TCB 槽位、不留半成品 |
| 释放时机 | 删非当前任务：**立即回收**；自删 / 删当前任务：PendSV 存完上下文后**延迟一次切换回收** |
| 碎片控制 | 块头固定 8 B 开销；相邻空闲块必合并；不搬迁活动栈（避免踩正在用的栈），无法满足的超大请求由「最大空闲块」统计提前识别 |
| 对外接口 | `jmk_task_create_ex(fn, arg, prio, name, stack_bytes)`；`jmk_stack_pool_{bytes,used,free,largest}()` |

**为什么用独立池而不是砾堆**：

1. 砾堆按 4 B 粒度且 `jm_run()` 每次都会 `jm_heap_init()` 重置整堆，任务栈放进去语义上会被"清掉"；
2. 任务栈要求 8 字节对齐与固定哨兵（0xA5A5A5A5）扫描，独立池不会被 VM 对象分配干扰；
3. 栈池耗尽与脚本 OOM 互相隔离，失败原因可区分。

块的布局：`[size<<1 | free][next] [载荷 ...]`；分配时若剩余 ≥ 8 B 载荷则拆分，否则整块给出。`size` 以字为单位且必为偶数，故 LSB 借给空闲标志。

### 5.2 静态兼容路径

编译加 `-DJMK_USE_STATIC_STACKS=1` 即回到 `6 × 512 B + 空闲 256 B` 固定数组：

- 现有 `led` / `log` 示例代码与行为不变；
- `jmk_task_create_ex()` 只接受 `stack_bytes <= 512`，更大的请求返回 -1；
- 栈池统计函数按固定槽位估算，示例仍可运行；
- 该路径下删除任务不回收内存（槽位复用时重建栈），与旧版一致。

### 5.3 RAM 预算（实测，动态默认）

| 区块 | 字节 | 说明 |
|---|---:|---|
| `jm_heap` | 6144 | 砾运行时静态堆 |
| `jm_state` | 4344 | VM 状态 + 栈槽 + 全局表 |
| `jmk_stack_pool` | 3200 | 动态任务栈池（替代原 3 KB 静态栈） |
| `jmk_tasks` | 216 | 6 × 36 B TCB |
| `jmk_idle_tcb` | 36 | 空闲任务 TCB |
| 串口格式化缓冲 | 128 | `port_log_u32` 用 |
| 就绪队列 / 池头 / tick 等 | ≈68 | |
| IPC 记账（`jmk_wait_obj` + `jmk_wait_result`） | 30 | 6 × 指针 + 6 × 结果字节，见第六节 |
| IPC 示例（队列控制块 32 + 调用方缓冲 32 + 信号量 12 × 2） | 88 | 在 `main.c`，不属于内核 |
| 对齐填充 | 2 | |
| `.data` | 4 | |
| **合计（RAM）** | **14260** | 占 20 KB 的 **69.63%**（text 17648 / data 4 / bss 14252） |
| 其中主栈 MSP 预留 | 2048 | 中断与异常使用 |
| **剩余可支配** | **≈4172** | |

Flash：**17652 B / 64 KB（26.93%）**。比上一版（17328 B）只多 324 B，因为未被示例调用的 `*_from_isr` 变体被 `-Wl,--gc-sections` 裁掉了；只编译 `jmk.o` 时新代码为 3117 B（旧 1653 B）。

**动态化后栈池上限怎么定**：设栈池为 P 字节，则扣除 MSP 预留后的余量 ≈ `7490 - P`。

| 栈池 P | 余量（扣除 2 KB MSP） | 评价 |
|---:|---:|---|
| 3200（默认） | ≈4292 | 6 个 512 B 任务（6×520=3120，余 80 B）刚好够，留足中断余量 |
| 4096 | ≈3394 | 想让任务栈普遍变大时的折中 |
| 6144 | ≈1346 | **建议上限**：再大就会侵蚀中断栈余量 |

当前默认配置下的实际能力：空闲任务占 264 B；常规示例（idle+led+log）占 1304 B；带 churn 示例时（4 个默认任务 = 1824 B）仍可一次性给新任务最大 **1368 B** 的单个栈。

**为什么堆是 6 KB**：12 KB 时只剩 3.7 KB，连 3 KB 任务栈都放不下；6 KB 能保证「你好」等示例与中等脚本正常运行。若脚本堆吃紧可回调到 8 KB，但扣除主栈后只剩约 0.3 KB 余量，不建议。

## 六、任务间通信（信号量 / 消息队列）

对外接口（`jmk.h`）：

| 对象 | 接口 | 说明 |
|---|---|---|
| 信号量 | `jmk_sem_init(s, initial, max)` / `jmk_sem_wait(s, timeout)` / `jmk_sem_post(s)` / `jmk_sem_post_from_isr(s, &woken)` | `max = 1` 即二值信号量，`max > 1` 为计数信号量 |
| 消息队列 | `jmk_queue_init(q, buf, item_size, capacity)` / `jmk_queue_send(q, item, timeout)` / `jmk_queue_recv(q, item, timeout)` / `jmk_queue_send_from_isr(q, item, &woken)` | 槽位内存由调用方提供 |

**阻塞语义**

| 项 | 约定 |
|---|---|
| 超时单位 | 毫秒，基于 1 ms tick；`0`（`JMK_NO_WAIT`）立即返回，`JMK_WAIT_FOREVER` 一直等 |
| 返回值 | `0` 成功；`-1` 超时；`-2` 参数非法；`-3` 上下文不允许；`-4` 计数/队列已满 |
| 唤醒顺序 | **高优先级先醒，同优先级 FIFO**——与就绪队列同一规则，等待链按优先级插入 |
| 中断里 | 只能「给出/发送」，用 `*_from_isr`；不能等待，满了直接返回 `-4` |
| 优先级反转 | **本期不处理**：信号量没有持有者概念，继承需要互斥量语义 |
| 虚假唤醒 | 允许。等待方用「检查 → 阻塞 → 再检查」循环，唤醒只表示条件可能已满足 |

**为什么队列缓冲由调用方提供**

1. RAM 只剩约 4.2 KB，内核无法预知消息大小与深度；把容量写死在内核里等于替所有业务做错误假设。
2. 队列控制块固定 32 B，缓冲可以是静态数组、砾堆分配、或复用的同一块内存，深度与元素大小由调用方决定。
3. 避免「内核 + 调用方各分配一份」的双份开销：发送/接收只做一次 `memcpy`。

**临界区与调度交互**

- 等待链、计数、队列读写都在 `crit_enter()` / `crit_exit()`（PRIMASK）里完成，临界区只做指针与计数的短操作。
- 「检查条件 + 挂入等待链」在同一临界区内完成，「给出 + 唤醒」也在同一临界区内完成，因此**不会丢唤醒**。
- 临界区内**只挂 PendSV（`SCB_ICSR = PENDSVSET`），绝不直接调用 `jmk_schedule()`**；真正的切换发生在中断/临界区退出之后。
- `*_from_isr` 同样只改结构 + 挂 PendSV；PendSV 优先级最低，等 ISR 退出后才切换。`woken` 告诉调用方是否唤醒了更高优先级任务。
- 删除任务时先从等待链摘下（`ipc_unlink`），避免等待链留下悬空 TCB。

**记账开销**：不往 TCB 加字段（保持 36 B 布局与 SWD 解析不变），只用两张 6 项小表：`jmk_wait_obj` 24 B + `jmk_wait_result` 6 B = **30 B**。等待链借用 TCB 的 `next` 指针（阻塞任务不在就绪队列，不冲突）。

## 七、验证方式（无需 ST-LINK）

烧录后仅看串口即可（默认 `JMK_IPC_DEMO=1` 看第 6 条；切到 `-DJMK_IPC_DEMO=0` 时看 1–5 条）：

1. `log` 任务每秒打印 `秒计数` 与 `uptime(ms)`，相邻两次差值应≈1000 ms（判断 tick 精度与切换开销）。
2. `led` 任务 250 ms 翻转 PC13，与打印节奏独立，说明两者在交替运行。
3. 每 5 次打印附带各任务栈峰值；超过自身栈容量 80% 会输出「接近溢出!」。
4. 若串口无输出但 PC13 仍闪，说明调度器在跑、只是 UART 接线问题；若板子完全静止，才怀疑 HardFault（本阶段未装故障打印）。
5. 栈动态分配示例：开机会打印 6 轮 `[栈池] 第 N 轮 创建前/建删后/回收后: 已用=… 空闲=… 最大空闲块=… 砾堆已用=…`。每轮「回收后」的三个数字应与「创建前」完全一致；子任务 A 退出前还会打印自身栈峰值（约 100 B 量级）。若数字逐轮上涨，即为栈泄漏。
6. 任务间通信示例：开机先打印 `[同步] 队列缓冲: 8 槽 × 4 B = 32 B…`，紧接着 `[同步] 超时自检通过：100 ms 无事件返回 -1`（说明 tick 超时摘链正确）；之后每 200 ms 一条 `[同步] 收到 seq=N 累计=… 栈峰值=… 队列余量=0`。`seq` 连续递增、`队列余量` 恒为 0 表示生产者/消费者配平；出现 `队列满，丢弃` 说明消费端被长时间阻塞；`累计` 必须严格 +1 递增。

## 八、已知限制（留给后续阶段）

- 砾程序仍只在 `main` 里单线程执行一次；任务里还没有独立 VM 状态（JM8 处理）。
- 有信号量与队列，但**无优先级继承、无互斥量、无事件组**；二值信号量当互斥用时存在优先级反转风险（低优先级持锁被中优先级抢占），正式互斥语义需要「持有者 + 继承」字段，留到后续里程碑。
- `*_from_isr` 变体已实现但示例未调用，因此会被 `--gc-sections` 裁掉；上板验证它需要接一路定时器中断（未烧录，等授权）。
- 队列没有「发送/接收完成回调」；队列满/空时的策略（丢弃、覆盖、阻塞）由调用方自己选，内核只提供返回值。
- 无挂起/恢复；同优先级轮转粒度为「主动让出或阻塞」，暂不做时间片强制轮转。
- 任务栈默认 512 B，可用 `jmk_task_create_ex()` 指定大小；栈池不足时创建失败返回 -1，无栈溢出检测（仅靠哨兵水位观察）。
- 栈池有空闲链合并，但不做搬移压缩；长期运行、大小混杂的任务反复建删仍可能产生无法利用的空洞，可用 `jmk_stack_pool_largest()` 监控。
