# 设计：语言层任务（VM 内部绿色线程）

> 状态：**纸面设计，未实现**。本轮不改 `runtime/`、`compiler/` 的任何实现代码。
> 日期：2026-11-08　关联：[原生函数表.md](原生函数表.md)（Native ABI v1）、[路径图.md](路径图.md)
> 结论：采用方案 A。新建/让出/延时/等待全部在 VM 内完成，`.jsh` 的任务跑在**一个** JMK 任务里，ABI v1 不动、native 表不动。

---

## 0. 一句话模型

```
JMK 调度器（抢占、固定优先级、1 ms tick）
├─ idle
├─ led    C 任务，不碰 VM
├─ log    C 任务，不碰 VM
└─ vm     prio 2，C 栈 1024 B，唯一进入 jm_run 的任务
   └─ 绿色调度器（协作、FIFO、无优先级；等待 = 非阻塞探测 + 让出重试）
      ├─ T0 root（.jsh 主流程）
      ├─ T1 子任务（≤3 个）
      ├─ T2 子任务
      └─ T3 子任务
```

`.jsh` 的任务**不是** JMK 任务，也不会新建 JMK 任务。它们共享 `vm` 这一个 JMK 任务的 C 栈，各自的执行上下文（值栈切片、帧栈切片、try 栈、闭包体）放在 `JmState` 里。

## 1. 调度模型

### 1.1 谁跑在哪里

| 层 | 实体 | 调度者 | 抢占 |
|---|---|---|---|
| 内核层 | `idle` / `led` / `log` / `vm` | JMK | 是，固定优先级 |
| 语言层 | root + ≤3 个子任务 | VM 绿色调度器 | **否，纯协作** |

- 绿色任务只在四个点让出：`让出()`、`延时()`、`队列/信号量等待`（§3.4）、任务退出/故障。`创建` 不让出，见下。
- 绿色调度器不做优先级、不做时间片；就绪任务按槽位号轮转（0→1→2→3→0），保证每个任务都能推进。
- 新建任务**不立即切换**：`创建` 只登记并返回句柄，父任务继续执行到下一个让出点。这样同一份 `.jsh` 的主机/板上输出顺序可预期。

### 1.2 `led` / `log` 还存不存在

存在，且**不改**。它们是 JMK C 任务，只碰 JMK 队列/信号量和 GPIO，不读不写 `JmState`。`JMK_IPC_DEMO` 的生产者/消费者演示继续有效。

语言层的队列/信号量（`.jsh` 里的 `队列创建` 等）与 `led`/`log` 用的 C 队列是两套对象，互不共享。

### 1.3 vm 被 JMK 抢占时，绿色线程为什么不会被破坏

三条不变量：

1. **`JmState` 只有一个写者**：只有 `vm` 任务进入 `jm_run`/`jm_execute`。`led`/`log`/ISR 都不碰它。
2. **绿色上下文不在 C 栈上**：值栈指针、帧指针、try 栈深度、挂起原因都存在 `JmState.tasks[]` 里。JMK 抢占 `vm` 时，被保存/恢复的是 `vm` 的 C 栈（汇编切换），`JmState` 原封不动。
3. **ISR 只碰内核对象**：中断路径仍是 `EXTI_IRQHandler → jmk_queue_send_from_isr`，不调用任何绿色 API、不进入 VM。

因此 JMK 抢占对绿色线程是**透明**的：抢占期间整个绿色世界一起暂停，恢复后从同一条指令继续。不需要锁，也不允许在 ISR 里调用 `创建/让出/延时/队列等待`（见 §6）。

### 1.4 根任务与程序结束

- `jm_run` 启动时创建 root（槽位 0），从 `.jmb` 入口开始执行。
- root 正常返回 → 程序结束：所有子任务直接作废，`jm_run` 返回 0，堆随下一次 `jm_run` 重置。
- 任何任务（含子任务）出现未捕获错误 → 整个 VM 停止，`jm_run` 返回 -1，错误走现有 `jm_last_error()` 通道。**没有按任务隔离的错误域**。

### 2.1 现状基线（实测）

| RAM 余量 | **5 540 B** |

### 2.3 分配方案（N = 4，含 root）

| 任务 | 值栈槽 | 值栈字节 | 帧栈 | try 栈 |
|---|---:|---:|---:|---:|
| root（T0） | **512（不变）** | 2 048 | 32（不变） | 8（不变） |
| 每个子任务 T1–T3 | **96** | 384 | **24**（144 B） | 1（6 B） |

- **root 不缩水**：现有 `.jsh` 程序（不建任务）行为与今天完全一致，没有隐性回归。
- 子任务 96 槽的依据：任务体是独立函数，通常只有循环变量、实参和少量临时值。**已实测**（`-DJM_STACK_WATERMARK=1`）：五套回归 + 14 个代表示例的最高值是 45 槽（斐波那契轮），其余 ≤ 12 槽；递归斜率 4 槽/层、基数 5 槽，96 槽约合 22 层递归。对 MCU 上的任务体够用，**冻结 96**（不再按 128 估）。
- **主 VM 的值栈另有上板实测（2026-11-09，N15）**：斜率 **5 槽/层、基数 8 槽**，递归 30 层用 **158 / 512 槽**；深度 31 起先撞 `JM_MAX_FRAMES = 32` 报 E021（此时只用了 160 槽）。也就是说主 VM 的递归上限由帧数决定，88 槽的按槽估算不适用于主上下文。详见 [路径图](路径图.md) §10.2 N15。
- **帧栈 24 帧（与 96 槽对齐）**：帧栈和值栈是两个独立的栈，限住递归深度的是帧栈（每次调用 1 帧，不占槽位）。按 4 帧算，子任务在深度 5 就撞 `E021`，96 槽根本用不满。取 24 帧让帧不再先于槽位耗尽（96 槽 ≈ 22 层，24 帧留 2 层余量）。代价：24 × 6 B = 144 B/任务，三任务合计 432 B，比 4 帧方案多 **360 B**。
- 96 槽不够时的调整：每子任务提到 128 槽，新增 3 × 32 × 4 B = 384 B，余量降到约 **3 402 B**；不要动 root 的 512 槽。

### 2.4 最坏情况余量

- 静态新增 1 754 B：14 940 + 1 754 = **16 694 B / 20 480 B**（81.51%），余 **3 786 B**。
- 三个子任务全部创建、各自用满 96 槽 / 24 帧 / 4 层 try：仍余 **3 732 B**（切片已预留在静态区，不随使用再涨）。
- `vm` C 栈：峰值 368 B + 绿色调度器新增预算 ≤ 96 B + 等待实参副本 ≤ 16 B = ≤ 480 B，余 ≥ 544 B。
- 砾堆 6 144 B 不变；任务体闭包、捕获值从这个堆分配，所以「4 个任务 + 大量闭包」仍可能先触发 `E017 堆内存耗尽`，这与任务数无关。

## 3. 阻塞点与边界

### 3.1 逐项结论

| 操作 | 现在 | 绿色线程后 | 说明 |
|---|---|---|---|
| `创建(任务体)` | 不存在 | **绿色调度**（`OP_TASK_SPAWN`） | 登记槽位、初始化上下文，父任务继续跑 |
| `让出()` | native → `jmk_yield()` | **绿色调度**（`OP_TASK_YIELD`） | 有别的就绪任务就切；没有才 `jmk_yield()` 给 `led`/`log` 让一次 |
| `延时(ms)` | native → `jmk_delay(ms)`，整个 vm 睡 | **绿色调度**（`OP_TASK_SLEEP`） | 见 §3.2 |
| `队列接收(q[, t])` | native `jmk_queue_recv`，阻塞整个 vm | **绿色等待**（`OP_TASK_WAIT`） | 探测 1 次 → 挂起 1 tick → 重试；见 §3.4 |
| `队列发送(q, v, t>0)` | 队列满时阻塞整个 vm | **绿色等待**（`OP_TASK_WAIT`） | 同上 |
| `信号量等待` | 阻塞整个 vm | **绿色等待**（`OP_TASK_WAIT`） | 同上 |
| `队列发送(q, v, 0)` / `信号量给出` | 非阻塞 | 非阻塞，不变 | 不会让出 |
| `引脚.*` / `ADC.*` / `定时器.*` / `等待毫秒` | 同步阻塞 vm | **不变** | 长忙等会冻结所有绿色任务，语言卡要写明 |
| `led` / `log` C 任务 | JMK | 不变 | 与绿色线程无交互 |

### 3.2 `延时` 时 vm 该不该跟着睡

**该睡，但不是固定睡 200 ms。**

- 若还有别的就绪绿色任务：立即切换到它，vm 一秒都不睡。
- 若无就绪任务、但有睡眠任务：`vm` 调 `jmk_delay(最近到期时刻 - jmk_ticks())`，睡到**最近一个**绿色任务到期，醒来后把它标成就绪再调度。
- 若既无就绪也无睡眠任务、root 还活着：本版的等待一律带 `wake_tick`（§3.4.2），不存在「无限期挂起等外部事件」的状态，所以这只可能是状态机不变量被破坏（例如 root 被错误标记为 BLOCKED）。按 `E039` 内部错误终止，不做空转轮询。

所以「绿色线程睡 200 ms」在 JMK 看来可能是 200 ms，也可能被切成若干段（期间有别的任务到期/被创建），取决于其他任务。

### 3.3 为什么等待必须离开 native

绿色切换的前提是**回到解释器循环**再保存/恢复上下文。`队列接收` 是 native 调用，一旦进入 `jmk_queue_recv(ms>0)` 就阻塞在 C 栈里，回不到解释器，插不进「让别的绿色任务先跑」。

这个代价不能接受：两个 `.jsh` 任务做生产者/消费者时，A 卡在队列上，B 也一起停——而「两个语言级任务互相传数据」正是本特性最主要的用途。

所以规则改成：**会等待的队列/信号量调用一律不许在 native 里阻塞**。native 只做一次非阻塞探测（`timeout = 0`），等待由 VM 在绿色层完成。

### 3.4 绿色等待：队列与信号量

#### 3.4.1 落地方式：VM 指令，不是编译器展开

两个候选：

- **甲（编译器展开）**：把 `队列接收(q, t)` 降级成「调用 `队列接收(q, 0)` → 判空 → `延时(1)` → 回跳」的循环。
- **乙（VM 指令）**：新增绿色感知指令 `OP_TASK_WAIT`，VM 自己完成「探测 → 挂起 → 到期重试 → 返回」。

**选乙。** 四条理由：

1. **字节码体积**：甲要在每个调用点展开「算截止 tick、探测、判空、判到期、睡 1 tick、回跳」，保守 18–24 B；一个生产者/消费者程序两三个调用点就是 50–70 B 的重复代码。乙是 2 B 指令（操作码 + 1 B 种类）+ 一份共享实现。
2. **时钟源**：甲要求语言层能读 tick 来算截止时间，而砾现在没有这个内建；补一个 `毫秒()` 等于把内部时钟暴露成语言 API，还要处理回绕。乙在 VM 内部用 `jm_port_millis()`，语言面零新增。
3. **语义分叉**：甲只对直接调用生效；一旦写成 `令 f = 队列接收` 再 `f(q, 100)`，展开失效、退回阻塞语义，同一个函数两种行为。乙把这三个名字定为「只能直接调用」（§4.6），这类写法编译报错，边界干净。
4. **一份实现，两个平台**：主机与板级共用同一份 VM，探测都走同一张 native 表；甲等于把调度逻辑复制进字节码，两边还得保证生成的展开代码一致。

**对 `.jmb` 的影响：只加一个操作码，不动任何既有结构。**

- `OP_TASK_WAIT`（编号 41）带 1 字节立即数 = 等待种类：`0` 队列接收、`1` 队列发送、`2` 信号量等待。
- 实参照旧压在值栈上，布局与现有 native 调用完全一致（栈顶是最后一个实参）。
- 不新增指令编码形式，不改头部/常量表/名字表/类表，**不需要提升字节码版本号**。
- 旧 `.jmb` 里这些调用仍是 `OP_CALL`，跑起来保持原阻塞语义——本项目每次构建都从源码重编，不做迁移。

VM 执行 `OP_TASK_WAIT` 的步骤：

1. **校验实参**：句柄是整数；超时是 0–60000 的整数。不合法按现有原生错误码 `JM_NE_TYPE` / `JM_NE_PARAM` 报错，文案与 native 一致。这一步必须在 VM——探测时传的是 0，native 里那份超时校验被绕过。
2. `deadline = jm_port_millis() + timeout`。
3. 把实参复制到本地小数组（最多 3 个 `JmValue` = 12 B，在 C 栈上），把超时槽改成 0，调 `jm_native_call(id, tmp, nargs, &out)`。
4. 结果不是超时值（队列接收是 `空`，队列发送/信号量等待是 `假`）→ 压结果、继续下一条。
5. 是超时值且 `jm_port_millis() >= deadline` → 压超时值返回，与阻塞版返回值完全一致。
6. 否则挂起当前任务（`state = SLEEPING`，`wake_tick = now + 1`），切走；醒来从第 3 步重来。

挂起时帧里的 `ip` **回退到本条指令起点**，醒来重新执行整条（探测是幂等的，实参也还在自己的值栈上，不会被弹掉）。

#### 3.4.2 重试节奏与唤醒延迟

- 重试间隔固定 **1 tick = 1 ms**，时钟走 JMK 的 SysTick：板上 `jm_port_millis()` 就是 `g_ms`，与 `jmk_ticks()` 同一个中断、同一个 1 ms 周期。
- 挂起后先看有没有别的 READY 任务：有就**立刻切过去，不等 tick**；只有「全都在睡/等」时才让 vm 调 `jm_port_sleep_ms(最近 wake_tick - now)`。所以生产者发完数据只要它让出（让出、延时、退出），等待方在**同一个 tick 内**就被唤醒。
- 唤醒延迟量级：**最好 0 tick**（对方主动让出，只花一次调度，几微秒）；**最坏 1 tick + 一次调度**（对方是纯计算循环、不主动让出）；**中位 1 ms**。
- 等待中的任务同样带 `wake_tick`，因此 §3.2 的「无就绪也无睡眠」仍然不可达，`E039` 兜底逻辑不变。

#### 3.4.3 CPU 代价

前提：STM32F103 @72 MHz，1 tick = 1 ms。一次探测 = `jm_native_call` 分派 + `jmk_queue_recv(0)` ≈ 40–60 周期 ≈ **0.6–0.9 µs**；一次「醒来 + 上下文切换 + 回到解释器」≈ 100–150 周期 ≈ **1.4–2.1 µs**。

| 场景 | 每毫秒开销 | 占 CPU |
|---|---:|---:|
| 没有任务在等 | 0（vm 睡着，SysTick 只唤醒内核） | 0 |
| 1 个任务在等 | 切换 ≈ 2 µs + 探测 ≈ 0.8 µs ≈ 3 µs | ≈ 0.3% |
| 3 个任务都在等 | 切换 ≈ 2 µs + 3 × 0.8 µs ≈ 4.4 µs | ≈ 0.45% |

- **结论：有等待者时 vm 每毫秒醒一次，代价每毫秒 3–5 µs；按最坏 8 µs 估上限约 0.8% CPU。** 这不是「可接受」的口头判断，是上面两个周期数乘出来的。
- 开销随「同时在等的人数」线性增长，**与等待时长无关**：等 10 ms 和等 60 s 的每秒开销一样。
- 没有任何任务在等时开销严格为 0，程序空闲时 vm 仍然整段睡在 `jmk_delay` 里。
- 若实测偏高，唯一旋钮是把重试间隔改成 1→2→4→8 ms 退避（牺牲最多 8 ms 唤醒延迟）。**本轮不做**，先用 1 tick 保延迟，见 §6 第 6 条。

#### 3.4.4 信号量等待与非阻塞查询

- `信号量等待(s, t)`：与 `队列接收` 同一套（种类 2），探测走 `jmk_sem_wait(s, 0)`，超时值是 `假`。
- 带超时的 `队列发送(q, v, t)`：种类 1，探测走 `jmk_queue_send(q, &v, 0)`，满则 `假`。第 3 步复制实参时**值槽保留原值，只把超时槽改成 0**。
- `队列数量(q)`、`队列发送(q, v)`（无超时）、`信号量给出`、引脚读写等本来就是非阻塞的：仍然是普通 `OP_CALL`，不进 `OP_TASK_WAIT`，不让出，行为与现在完全一样。
- 编译器规则：这三个名字**带超时实参**时发 `OP_TASK_WAIT`（超时是字面量 0 也照发，运行时探测一次即返回，少一条编译期特判）；**不带超时实参**时发普通 `OP_CALL`（本来就非阻塞，不需要等待）。

#### 3.4.5 能力边界（替代原「冻结整个 vm」的结论）

原设计里「队列/信号量等待会冻结整个 vm、两个 `.jsh` 任务做不了生产者/消费者」这条**作废**。新边界：

| 行为 | 现在 |
|---|---|
| 两个 `.jsh` 任务用队列做生产者/消费者 | **支持**；等待方按 1 tick 重试，对方让出时 0 tick 交接 |
| `信号量等待` 做任务间事件 | **支持**，同上 |
| 中断 → 队列 → 绿色任务 | **支持**：ISR 侧 `jmk_queue_send_from_isr` 不变，任务侧走绿色等待 |
| `引脚.*` / `ADC.*` / `定时器.*` / `等待毫秒` 的长忙等 | **仍冻结整个 vm**——这些是真的同步忙等，不是可重试的等待 |
| ISR 里建任务 / 让出 / 等待 | 仍禁止（§6） |

#### 3.4.6 RAM 变化

- `JmGreenTask` 从 32 B 涨到 **36 B**：删掉预留的 `wait_arg`（2 B），加 `wait_kind`（1 B）、`wait_native`（1 B）、`deadline_tick`（4 B）。4 × 36 = **144 B**（原 128 B，**+16 B**）。
- `JmState` 加 `wait_native[3]`：载入时把三种等待解析出的 native id 缓存下来，运行期不查名。**4 B**（3 B + 1 B 对齐）。
- 新增合计 **1 754 B**（原 1 374 B，**+380 B**：等待字段 +20 B、24 帧调整 +360 B）：14 940 + 1 754 = **16 694 / 20 480 B**，余 **3 786 B**。
- 栈切片**不用调**：等待不占值栈，实参在被挂起期间留在自己的值栈切片上，最多 3 个槽。`vm` C 栈加 ≤16 B 的实参副本，峰值从「368 + 96」变成「368 + 96 + 16 ≤ 480 B」，余 ≥ 544 B。
- 若后续把子任务值栈从 96 提到 128 槽，按 §2.3 的 +384 B 算，余量降到约 **3 402 B**。

## 4. `JmState` 的具体改动形状

### 4.1 新增任务结构

```c
#define JM_MAX_GREEN_TASKS   4u   /* root + 3 子任务 */
#define JM_CHILD_STACK_SLOTS 96u
#define JM_CHILD_FRAMES      24u
#define JM_CHILD_TRIES       1u

typedef struct {
    JmValue   *stack;       /* 指向自己的值栈切片 */
    JmFrame   *frames;      /* 指向自己的帧栈切片 */
    JmTry     *tries;       /* 指向自己的 try 栈切片 */
    uint16_t   stack_cap;   /* 槽数 */
    uint16_t   sp;
    uint8_t    frames_cap;
    uint8_t    fp;
    uint8_t    tries_cap;
    uint8_t    tp;
    uint8_t    state;       /* FREE / READY / RUNNING / SLEEPING / BLOCKED / DEAD */
    uint8_t    slot;        /* 0..3，对外句柄 = slot（root 不暴露） */
    uint8_t    wait_kind;   /* 0 无 / 1 队列接收 / 2 队列发送 / 3 信号量等待 */
    uint8_t    wait_native; /* wait_kind 对应的 native id；无等待为 0 */
    uint32_t   wake_tick;   /* 下次可运行 tick：延时到期 / 等待重试 */
    uint32_t   deadline_tick; /* 绿色等待的截止 tick */
    JmValue    body;        /* 任务体闭包；root 为 UNDEF */
} JmGreenTask;             /* 36 B（含对齐），实现时用 static_assert 锁定 */
```

### 4.2 `JmState` 的字段变化

新增：

```c
JmValue    child_stack[JM_MAX_GREEN_TASKS - 1][JM_CHILD_STACK_SLOTS];
JmFrame    child_frames[JM_MAX_GREEN_TASKS - 1][JM_CHILD_FRAMES];
JmTry      child_tries[JM_MAX_GREEN_TASKS - 1][JM_CHILD_TRIES];
JmGreenTask tasks[JM_MAX_GREEN_TASKS];
uint8_t     ntask;
uint8_t     current;
uint8_t     wait_native[3];  /* 种类 1..3 → native id，载入时解析 */
```

现有字段保持，但解释器的取用方式改为「当前任务指针」：

- `st->stack` / `st->frames` / `st->tries` 由数组改为**指向当前任务切片的指针**（root 指向原来的三个数组，子任务指向 `child_*`）。
- `st->sp` / `fp` / `tp` 在切换时整体存入/取出 `tasks[current]`。
- `globals`、`const_cache`、堆、常量区、名字表、类表**不拆**，所有任务共享。

### 4.3 解释器循环的切换点

- `jm_execute` 改成「外层调度循环 + 内层取指循环」。内层判断 `st->tasks[st->current].state` 变化后跳出，外层挑选下一个 READY。
- 切换前必须 `f->ip = ip`（把当前指令位置写回帧），切换后从 `frames[fp]` 重新推导 `f` / `code` / `ce` / `clen` / `cur_nlocals` / `ip`。这些局部变量不能跨任务复用。
- `OP_CALL` 调闭包时把捕获值填进新帧的逻辑（`jm_vm.c` 现有 `JM_T_CLOSURE` 分支）抽成 `jm_green_push_frame()`，`OP_TASK_SPAWN` 复用同一份，避免两套捕获槽语义。
- `OP_TASK_WAIT` 也在内层循环里处理：探测成功就地压结果继续；失败则置 SLEEPING、`wake_tick = now + 1`、跳出内层。挂起时把帧里的 `ip` 回退到本条指令起点，醒来重放整条（探测幂等，实参仍在自己的值栈切片上）。
- `OP_RETURN` 在 `fp == 0` 时不再 `goto done`，改为「任务退出」：root → 程序结束；子任务 → 标 DEAD、释放 `body`、切走。

### 4.4 `jm_run` 的重置语义

- 仍然 `memset(JmState)` + 重置 globals/const_cache + `jm_heap_init()`。
- 新增：清空 `tasks[]`，把槽位 0 初始化为 root（`stack` 指向 `st->stack`，`frames` 指向 `st->frames`，`tries` 指向 `st->tries`，容量为现有宏），`ntask = 1`，`current = 0`。
- `jm_run` 返回时**不保留任何任务**：所有子任务、闭包、堆对象一起作废。不存在「跨 `jm_run` 存活的任务」。
- 句柄 `1..3` 在一次 `jm_run` 内**不复用**：子任务退出后槽位保持 DEAD 直到本次运行结束。因此单次运行最多创建 3 个任务；这是为避免「旧句柄指向新任务」的歧义，见 §6。

### 4.5 对现有机制的影响

| 机制 | 影响 |
|---|---|
| `TAG_*` / `JmValue` 编码 | **不变**。不新增标签，不把闭包塞进整数 |
| 闭包 `JmClosure` | **不变**。body 仍是 `code_idx + caps[]`，同一份堆、同一份镜像 |
| 函数值 `TAG_FUNC` | 可作为任务体；直接引用入口函数名的场景由编译器产出 `TAG_FUNC` |
| 异常栈 `tries` | **拆成 per-task**。root 仍 8 层，子任务 4 层；`尝试` 超过当前任务的层数报 `E028` |
| 全局变量 | 仍共享。协作切换只在让出点发生，不存在数据竞争，但也没有原子性保证 |
| `const_cache` | 共享，不变 |
| 堆 / 引用计数 | 共享，不变；任务退出时释放 `body` |
| `队列`/`信号量` native | 函数体与超时语义不变；带超时的直接调用改由 VM 用 `timeout=0` 反复调它（§3.4.1） |
| 原生表 | `任务` 表整体移除（7 张 → 6 张 / 23 项 → 21 项），`f103_native.c`、`jm_host_native.c`、生成头同步删表 |

### 4.6 编译期形态

新增 `compiler/src/vm_spec.rs`（与 `native_spec.rs` 平行），只放一个模块：

| 名字 | 参数 | 产出 |
|---|---|---|
| `创建` | 1（函数/闭包） | `OP_TASK_SPAWN` |
| `删除` | 1（任务句柄） | `OP_TASK_KILL`（42；见 §6 的 2026-11-08 变更） |
| `让出` | 0 | `OP_TASK_YIELD` |
| `延时` | 1（0–60000 ms） | `OP_TASK_SLEEP` |
| `队列接收` | 2（句柄, 超时） | `OP_TASK_WAIT`（种类 0） |
| `队列发送` | 3（句柄, 值, 超时） | `OP_TASK_WAIT`（种类 1） |
| `信号量等待` | 2（句柄, 超时） | `OP_TASK_WAIT`（种类 2） |

- `导入 任务` 由这份规格解析，不再查 native 表；拼错/参数个数仍报现有 `E113`/`E115`。
- 这六个名字是**编译期指令，不是值**：`令 f = 创建`、`令 g = 队列接收` 这类用法直接编译报错（新增一条编译错误，文案「任务/等待函数不能作为值使用」）。这样就不会出现「闭包当整数传、调用路径绕过调度器、以值调用绕过绿色等待」三个口子。
- 带超时实参的三个等待调用发 `OP_TASK_WAIT`；不带超时实参时仍发普通 `OP_CALL`（本来就非阻塞）。`队列接收(q, 0)` 这种字面量 0 也发 `OP_TASK_WAIT`，运行时探测一次即返回，避免编译期特判。
- `.jmb` 新增五个操作码（38/39/40/41/42；这是操作码编号空间，与 §5 的错误码 38/39 无关）。当前 0–37 已用，不需要改字节码版本号之外的结构；`OP_TASK_SPAWN` 操作数为 0（任务体在栈顶），`OP_TASK_WAIT` 操作数是 1 字节等待种类（§3.4.1），`OP_TASK_KILL` 操作数为 0（句柄在栈顶）。

## 5. 错误码

| 场景 | 码 | 文案 | 说明 |
|---|---|---|---|
| 任务体不是函数/闭包 | `E011`（复用 `E_NOT_CALLABLE`） | 这个值不能调用 | 与普通调用同码，detail 写「任务体必须是函数」 |
| 任务体形参个数 ≠ 0 | `E012`（复用 `E_ARGC`） | 实参个数不符 | 在 `创建` 时就检查代码对象 `nparams`，不等到子任务第一次执行 |
| 任务数超限（root+3 已满） | **`E038`（新增 `E_TASK_LIMIT`）** | 任务数超过上限 4 | 单次运行最多 3 次成功 `创建` |
| 其它新建失败（槽位/上下文不变量） | **`E039`（新增 `E_TASK_STATE`）** | 任务状态不允许新建 | 本版静态切片下理论上不可达，作为不变量兜底；出现即 bug |
| 子任务值栈溢出 | `E001`（现有 `E_STACK`） | 值栈溢出 | detail 写「任务 Tn 值栈溢出」 |
| 子任务调用层数过深 | `E021`（现有 `E_FRAMES`） | 调用层数太深 | 子任务 24 帧上限；正常路径上值栈（96 槽、4 槽/层 ≈ 22 层）先耗尽 |
| 子任务未捕获异常 | 原错误码 | 原文案 | 整个程序停止，不做任务级隔离 |

`jm_error.c` 的 `msg_for()` 追加 38/39 两条；ABI 的 `JM_NE_*`（30–34）不动。

绿色等待不新增错误码：实参类型/范围错误沿用 `JM_NE_TYPE`（30）/`JM_NE_PARAM`（31），只是校验点从 native 前移到 VM（探测传 0，native 那份校验被绕过）；等待种类找不到对应 native 时沿用 `E011`「未知原生函数」。

## 6. 本轮明确不做

1. **不做绿色抢占**：没有时间片、没有 tick 驱动的任务切换；只有显式让出点。
2. **不做优先级**：就绪任务按槽位轮转，不能指定优先级。
3. **不做杀任务 / 挂起 / 恢复 / 等待（join）**：任务只能自然结束；没有句柄回收，也没有「等子任务结束」。**（2026-11-08 部分作废：见本节末尾的变更记录）**
4. **不做任务句柄复用**：单次 `jm_run` 内最多创建 3 个任务，退出后的槽位不复用。
5. **不做跨任务共享可变状态的同步**：全局变量仍共享，但没有互斥、没有原子操作；协作切换只在让出点，用户要自己保证「让出前状态一致」。
6. **不做事件驱动的唤醒**：队列/信号量等待靠 1 tick 轮询（§3.4.2），不把绿色任务挂进 JMK 的等待链，也不让 native 注册唤醒回调——那要改内核等待结构。同样不做退避（1→2→4→8 ms）与等待优先级。
7. **不做 ISR 建任务 / ISR 让出**：中断里只能操作 JMK 对象。
8. **不做 per-task 堆、per-task 全局变量、多 VM 实例、多核**。
9. **不做任务名/调试视图**：`led`/`log` 的任务名机制不扩展到绿色任务。
10. **不改进程模型**：root 结束即程序结束，子任务随之作废；没有「后台任务比 main 活得久」。

**2026-11-08 变更（JM8 收尾）**

- 第 3 条部分作废：新增语言层 `删除(句柄)`（`OP_TASK_KILL`，操作码 42），用于取消一个**未在运行**的任务（READY / SLEEPING / 绿色等待中）：释放它的值栈切片与任务体，状态标 `DEAD`，返回 `真`。句柄非法、目标已 `DEAD`/`FREE`，或目标就是当前任务时返回 `假`（当前任务要用 `返回` 结束）。
- 删除不抛异常，也不新增错误码；主机与板级同一份 `jm_vm.c`，行为一致。
- 第 3 条里的「挂起/恢复/join」、第 4 条的「句柄复用」仍然**不做**：删除后的槽位保持 `DEAD`，单次 `jm_run` 内创建次数上限仍是 3（第 4 次 `E038`）。因此 `删除` 的价值是「提前取消并释放值栈/任务体」，不是「腾出槽位再建」。
- 回归夹具：`examples/任务删除.jsh`（建 → 删 → 重删 → 删根 → 删越界），基准 `tests/expected/任务删除.txt`。
