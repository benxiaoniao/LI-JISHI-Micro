# 设计：语言层任务（VM 内部绿色线程）

> 状态：**纸面设计，未实现**。本轮不改 `runtime/`、`compiler/` 的任何实现代码。
> 日期：2026-11-08　关联：[原生函数表.md](原生函数表.md)（Native ABI v1）、[路径图.md](路径图.md)
> 结论：采用方案 A。新建/让出/延时全部在 VM 内完成，`.jsh` 的任务跑在**一个** JMK 任务里，ABI v1 不动。

---

## 0. 一句话模型

```
JMK 调度器（抢占、固定优先级、1 ms tick）
├─ idle
├─ led    C 任务，不碰 VM
├─ log    C 任务，不碰 VM
└─ vm     prio 2，C 栈 1024 B，唯一进入 jm_run 的任务
   └─ 绿色调度器（协作、FIFO、无优先级）
      ├─ T0 root（.jsh 主流程）
      ├─ T1 子任务（≤3 个）
      ├─ T2 子任务
      └─ T3 子任务
```

`.jsh` 的任务**不是** JMK 任务，也不会新建 JMK 任务。它们共享 `vm` 这一个 JMK 任务的 C 栈，各自的执行上下文（值栈切片、帧栈切片、try 栈、闭包体）放在 `JmState` 里。

---

## 1. 调度模型

### 1.1 谁跑在哪里

| 层 | 实体 | 调度者 | 抢占 |
|---|---|---|---|
| 内核层 | `idle` / `led` / `log` / `vm` | JMK | 是，固定优先级 |
| 语言层 | root + ≤3 个子任务 | VM 绿色调度器 | **否，纯协作** |

- 绿色任务只在三个点让出：`让出()`、`延时()`、任务退出/故障。`创建` 不让出，见下。
- 绿色调度器不做优先级、不做时间片；就绪任务按槽位号轮转（0→1→2→3→0），保证每个任务都能推进。
- 新建任务**不立即切换**：`创建` 只登记并返回句柄，父任务继续执行到下一个让出点。这样同一份 `.jsh` 的主机/板上输出顺序可预期。

### 1.2 `led` / `log` 还存不存在

存在，且**不改**。它们是 JMK C 任务，只碰 JMK 队列/信号量和 GPIO，不读不写 `JmState`。`JMK_IPC_DEMO` 的生产者/消费者演示继续有效。

语言层的队列/信号量（`.jsh` 里的 `队列创建` 等）与 `led`/`log` 用的 C 队列是两套对象，互不共享。

### 1.3 vm 被 JMK 抢占时，绿色线程为什么不会被破坏

三条不变量：

1. **`JmState` 只有一个写者**：只有 `vm` 任务进入 `jm_run`/`jm_execute`。`led`/`log`/ISR 都不碰它。
2. **绿色上下文不在 C 栈上**：值栈指针、帧指针、try 栈深度、挂起原因都存在 `JmState.tasks[]` 里。JMK 抢占 `vm` 时，被保存/恢复的是 `vm` 的 C 栈（汇编切换），`JmState` 原封不动。
3. **ISR 只碰内核对象**：中断路径仍是 `EXTI_IRQHandler → jmk_queue_send_from_isr`，不调用任何绿色 API、不进入 VM。

因此 JMK 抢占对绿色线程是**透明**的：抢占期间整个绿色世界一起暂停，恢复后从同一条指令继续。不需要锁，也不允许在 ISR 里调用 `创建/让出/延时`（见 §6）。

### 1.4 根任务与程序结束

- `jm_run` 启动时创建 root（槽位 0），从 `.jmb` 入口开始执行。
- root 正常返回 → 程序结束：所有子任务直接作废，`jm_run` 返回 0，堆随下一次 `jm_run` 重置。
- 任何任务（含子任务）出现未捕获错误 → 整个 VM 停止，`jm_run` 返回 -1，错误走现有 `jm_last_error()` 通道。**没有按任务隔离的错误域**。

## 2. RAM 预算

### 2.1 现状基线（实测）

| 项 | 数值 |
|---|---:|
| 固件 RAM 已用 / 总量 | 14 940 B / 20 480 B（70.92%） |
| RAM 余量 | **5 540 B** |
| 值栈 | 512 槽 × 4 B = 2 048 B（root 独占） |
| 帧栈 | 32 帧 × 6 B = 192 B |
| try 栈 | 8 层 × 6 B = 48 B |
| 全局槽 / 常量缓存 | 1 024 B + 1 024 B |
| 砾堆 `JM_HEAP_SIZE` | 6 144 B（独立静态区） |
| `vm` C 栈 | 1 024 B，实测峰值 368 B |

### 2.2 新增静态内存（全部有实数）

| 项 | 计算 | 字节 |
|---|---|---:|
| `JmGreenTask tasks[4]` | 4 × 32 B（字段见 §4.1，含对齐） | 128 |
| 调度器游标（`ntask`/`current`/对齐） | 4 B | 4 |
| 子任务值栈 `child_stack[3][96]` | 3 × 96 × 4 B | 1 152 |
| 子任务帧栈 `child_frames[3][4]` | 3 × 4 × 6 B | 72 |
| 子任务 try 栈 `child_tries[3][1]` | 3 × 1 × 6 B | 18 |
| **合计** | | **1 374** |

### 2.3 分配方案（N = 4，含 root）

| 任务 | 值栈槽 | 值栈字节 | 帧栈 | try 栈 |
|---|---:|---:|---:|---:|
| root（T0） | **512（不变）** | 2 048 | 32（不变） | 8（不变） |
| 每个子任务 T1–T3 | **96** | 384 | 4 | 1 |

- **root 不缩水**：现有 `.jsh` 程序（不建任务）行为与今天完全一致，没有隐性回归。
- 子任务 96 槽的依据：任务体是独立函数，通常只有循环变量、实参和少量临时值；先按 96 槽落地，**实现时必须先加值栈高水位观测**（在 `PUSH_V` 处记录 `sp` 峰值），跑完五套回归和任务示例后再冻结这个数。
- 96 槽不够时的调整：每子任务提到 128 槽，新增 3 × 32 × 4 B = 384 B，余量降到约 **3 782 B**；不要动 root 的 512 槽。

### 2.4 最坏情况余量

- 静态新增 1 374 B：14 940 + 1 374 = **16 314 B / 20 480 B**，余 **4 166 B**。
- 三个子任务全部创建、各自用满 96 槽 / 4 帧 / 1 层 try：仍余 **4 166 B**（槽已预留在静态区，不随使用再涨）。
- `vm` C 栈：峰值 368 B + 绿色调度器新增预算 ≤ 96 B = ≤ 464 B，余 ≥ 560 B。
- 砾堆 6 144 B 不变；任务体闭包、捕获值从这个堆分配，所以「4 个任务 + 大量闭包」仍可能先触发 `E017 堆内存耗尽`，这与任务数无关。

## 3. 阻塞点与边界

### 3.1 逐项结论

| 操作 | 现在 | 绿色线程后 | 说明 |
|---|---|---|---|
| `创建(任务体)` | 不存在 | **绿色调度**（`OP_TASK_SPAWN`） | 登记槽位、初始化上下文，父任务继续跑 |
| `让出()` | native → `jmk_yield()` | **绿色调度**（`OP_TASK_YIELD`） | 有别的就绪任务就切；没有才 `jmk_yield()` 给 `led`/`log` 让一次 |
| `延时(ms)` | native → `jmk_delay(ms)`，整个 vm 睡 | **绿色调度**（`OP_TASK_SLEEP`） | 见 §3.2 |
| `队列接收(q[, t])` | native `jmk_queue_recv`，阻塞整个 vm | **仍走 JMK，阻塞整个 vm** | 本版边界；见 §3.3 |
| `队列发送(q, v, t>0)` | 队列满时阻塞整个 vm | **仍走 JMK，阻塞整个 vm** | 同上 |
| `信号量等待` | 阻塞整个 vm | **仍走 JMK，阻塞整个 vm** | 同上 |
| `队列发送(q, v, 0)` / `信号量给出` | 非阻塞 | 非阻塞，不变 | 不会让出 |
| `引脚.*` / `ADC.*` / `定时器.*` / `等待毫秒` | 同步阻塞 vm | **不变** | 长忙等会冻结所有绿色任务，语言卡要写明 |
| `led` / `log` C 任务 | JMK | 不变 | 与绿色线程无交互 |

### 3.2 `延时` 时 vm 该不该跟着睡

**该睡，但不是固定睡 200 ms。**

- 若还有别的就绪绿色任务：立即切换到它，vm 一秒都不睡。
- 若无就绪任务、但有睡眠任务：`vm` 调 `jmk_delay(最近到期时刻 - jmk_ticks())`，睡到**最近一个**绿色任务到期，醒来后把它标成就绪再调度。
- 若既无就绪也无睡眠任务、root 还活着：本版没有「绿色外部事件等待」，这只可能是状态机不变量被破坏（例如 root 被错误标记为 BLOCKED）。按 `E039` 内部错误终止，不做空转轮询。

所以「绿色线程睡 200 ms」在 JMK 看来可能是 200 ms，也可能被切成若干段（期间有别的任务到期/被创建），取决于其他任务。

### 3.3 队列/信号量为什么仍走 JMK（本版的硬边界）

绿色切换的前提是**回到解释器循环**再保存/恢复上下文。`队列接收` 是 native 调用，一旦进入 `jmk_queue_recv` 就阻塞在 C 栈里，无法把「让别的绿色任务先跑」这件事插进去。要让它们参与绿色调度，必须满足两个条件：

1. native 只做非阻塞探测（`timeout=0`）；
2. 由 VM 层（编译器标记的等待指令）负责「探测失败 → 挂起当前绿色任务 → 到期/事件唤醒后重试」。

第 2 条要新增 VM 指令并处理「native 函数被当值传递」的语义分叉，属于下一阶段（见 §6），本轮不做。因此本版明确：**在绿色任务里调用会阻塞的队列/信号量 API，会冻结整个 vm（包括所有绿色任务）**。这条必须写进语言卡，不能靠用户猜。

## 4. `JmState` 的具体改动形状

### 4.1 新增任务结构

```c
#define JM_MAX_GREEN_TASKS   4u   /* root + 3 子任务 */
#define JM_CHILD_STACK_SLOTS 96u
#define JM_CHILD_FRAMES      4u
#define JM_CHILD_TRIES       1u

typedef struct {
    JmValue   *stack;       /* 指向自己的值栈切片 */
    JmFrame   *frames;      /* 指向自己的帧栈切片 */
    JmTry     *tries;       /* 指向自己的 try 栈切片 */
    uint16_t   stack_cap;   /* 槽数 */
    uint16_t   sp;
    uint8_t    frames_cap;
    uint8_t    fp;
    uint8_t    tries_cap;
    uint8_t    tp;
    uint8_t    state;       /* FREE / READY / RUNNING / SLEEPING / BLOCKED / DEAD */
    uint8_t    slot;        /* 0..3，对外句柄 = slot（root 不暴露） */
    uint16_t   wait_arg;    /* 预留：将来绿色等待队列/信号量用 */
    JmValue    body;        /* 任务体闭包；root 为 UNDEF */
    uint32_t   wake_tick;   /* SLEEPING 时的到期 tick */
} JmGreenTask;             /* 32 B（含对齐），实现时用 static_assert 锁定 */
```

### 4.2 `JmState` 的字段变化

新增：

```c
JmValue    child_stack[JM_MAX_GREEN_TASKS - 1][JM_CHILD_STACK_SLOTS];
JmFrame    child_frames[JM_MAX_GREEN_TASKS - 1][JM_CHILD_FRAMES];
JmTry      child_tries[JM_MAX_GREEN_TASKS - 1][JM_CHILD_TRIES];
JmGreenTask tasks[JM_MAX_GREEN_TASKS];
uint8_t     ntask;
uint8_t     current;
```

现有字段保持，但解释器的取用方式改为「当前任务指针」：

- `st->stack` / `st->frames` / `st->tries` 由数组改为**指向当前任务切片的指针**（root 指向原来的三个数组，子任务指向 `child_*`）。
- `st->sp` / `fp` / `tp` 在切换时整体存入/取出 `tasks[current]`。
- `globals`、`const_cache`、堆、常量区、名字表、类表**不拆**，所有任务共享。

### 4.3 解释器循环的切换点

- `jm_execute` 改成「外层调度循环 + 内层取指循环」。内层判断 `st->tasks[st->current].state` 变化后跳出，外层挑选下一个 READY。
- 切换前必须 `f->ip = ip`（把当前指令位置写回帧），切换后从 `frames[fp]` 重新推导 `f` / `code` / `ce` / `clen` / `cur_nlocals` / `ip`。这些局部变量不能跨任务复用。
- `OP_CALL` 调闭包时把捕获值填进新帧的逻辑（`jm_vm.c` 现有 `JM_T_CLOSURE` 分支）抽成 `jm_green_push_frame()`，`OP_TASK_SPAWN` 复用同一份，避免两套捕获槽语义。
- `OP_RETURN` 在 `fp == 0` 时不再 `goto done`，改为「任务退出」：root → 程序结束；子任务 → 标 DEAD、释放 `body`、切走。

### 4.4 `jm_run` 的重置语义

- 仍然 `memset(JmState)` + 重置 globals/const_cache + `jm_heap_init()`。
- 新增：清空 `tasks[]`，把槽位 0 初始化为 root（`stack` 指向 `st->stack`，`frames` 指向 `st->frames`，`tries` 指向 `st->tries`，容量为现有宏），`ntask = 1`，`current = 0`。
- `jm_run` 返回时**不保留任何任务**：所有子任务、闭包、堆对象一起作废。不存在「跨 `jm_run` 存活的任务」。
- 句柄 `1..3` 在一次 `jm_run` 内**不复用**：子任务退出后槽位保持 DEAD 直到本次运行结束。因此单次运行最多创建 3 个任务；这是为避免「旧句柄指向新任务」的歧义，见 §6。

### 4.5 对现有机制的影响

| 机制 | 影响 |
|---|---|
| `TAG_*` / `JmValue` 编码 | **不变**。不新增标签，不把闭包塞进整数 |
| 闭包 `JmClosure` | **不变**。body 仍是 `code_idx + caps[]`，同一份堆、同一份镜像 |
| 函数值 `TAG_FUNC` | 可作为任务体；直接引用入口函数名的场景由编译器产出 `TAG_FUNC` |
| 异常栈 `tries` | **拆成 per-task**。root 仍 8 层，子任务 1 层；`尝试` 在子任务里超过 1 层报 `E028` |
| 全局变量 | 仍共享。协作切换只在让出点发生，不存在数据竞争，但也没有原子性保证 |
| `const_cache` | 共享，不变 |
| 堆 / 引用计数 | 共享，不变；任务退出时释放 `body` |
| 原生表 | `任务` 表整体移除（7 张 → 6 张 / 23 项 → 21 项），`f103_native.c`、`jm_host_native.c`、生成头同步删表 |

### 4.6 编译期形态

新增 `compiler/src/vm_spec.rs`（与 `native_spec.rs` 平行），只放一个模块：

| 名字 | 参数 | 产出 |
|---|---|---|
| `创建` | 1（函数/闭包） | `OP_TASK_SPAWN` |
| `让出` | 0 | `OP_TASK_YIELD` |
| `延时` | 1（0–60000 ms） | `OP_TASK_SLEEP` |

- `导入 任务` 由这份规格解析，不再查 native 表；拼错/参数个数仍报现有 `E113`/`E115`。
- 这三个名字是**编译期指令，不是值**：`令 f = 创建` 这类用法直接编译报错（新增一条编译错误，文案「任务.* 不能作为值使用」）。这样就不会出现「闭包当整数传、调用路径绕过调度器」的口子。
- `.jmb` 新增三个操作码（38/39/40；这是操作码编号空间，与 §5 的错误码 38/39 无关）。当前 0–37 已用，不需要改字节码版本号之外的结构；`OP_TASK_SPAWN` 的操作数是 0（任务体在栈顶）。

## 5. 错误码

| 场景 | 码 | 文案 | 说明 |
|---|---|---|---|
| 任务体不是函数/闭包 | `E011`（复用 `E_NOT_CALLABLE`） | 这个值不能调用 | 与普通调用同码，detail 写「任务体必须是函数」 |
| 任务体形参个数 ≠ 0 | `E012`（复用 `E_ARGC`） | 实参个数不符 | 在 `创建` 时就检查代码对象 `nparams`，不等到子任务第一次执行 |
| 任务数超限（root+3 已满） | **`E038`（新增 `E_TASK_LIMIT`）** | 任务数超过上限 4 | 单次运行最多 3 次成功 `创建` |
| 其它新建失败（槽位/上下文不变量） | **`E039`（新增 `E_TASK_STATE`）** | 任务状态不允许新建 | 本版静态切片下理论上不可达，作为不变量兜底；出现即 bug |
| 子任务值栈溢出 | `E001`（现有 `E_STACK`） | 值栈溢出 | detail 写「任务 Tn 值栈溢出」 |
| 子任务调用层数过深 | `E021`（现有 `E_FRAMES`） | 调用层数太深 | 子任务 4 帧上限 |
| 子任务未捕获异常 | 原错误码 | 原文案 | 整个程序停止，不做任务级隔离 |

`jm_error.c` 的 `msg_for()` 追加 38/39 两条；ABI 的 `JM_NE_*`（30–34）不动。

## 6. 本轮明确不做

1. **不做绿色抢占**：没有时间片、没有 tick 驱动的任务切换；只有显式让出点。
2. **不做优先级**：就绪任务按槽位轮转，不能指定优先级。
3. **不做杀任务 / 挂起 / 恢复 / 等待（join）**：任务只能自然结束；没有句柄回收，也没有「等子任务结束」。
4. **不做任务句柄复用**：单次 `jm_run` 内最多创建 3 个任务，退出后的槽位不复用。
5. **不做跨任务共享可变状态的同步**：全局变量仍共享，但没有互斥、没有原子操作；协作切换只在让出点，用户要自己保证「让出前状态一致」。
6. **不做绿色感知的队列/信号量等待**：`队列接收`、带超时的 `队列发送`、`信号量等待` 仍阻塞整个 vm（§3.3）。下一阶段才考虑 `OP_WAIT` + 非阻塞探测。
7. **不做 ISR 建任务 / ISR 让出**：中断里只能操作 JMK 对象。
8. **不做 per-task 堆、per-task 全局变量、多 VM 实例、多核**。
9. **不做任务名/调试视图**：`led`/`log` 的任务名机制不扩展到绿色任务。
10. **不改进程模型**：root 结束即程序结束，子任务随之作废；没有「后台任务比 main 活得久」。
