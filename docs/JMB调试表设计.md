# `.jmb` 调试表设计（JM10）

> 状态：设计稿，只定协议与取舍，不改代码。
> 关联：[微字节码规格.md](微字节码规格.md)、[路径图.md](路径图.md) 中的 H3 / H4 / JM10。

## 1. 目标与非目标

**目标**

1. 让 `.jmb` 自带「源码文件 + 行号 ↔ 指令流偏移」的映射，支撑：
   - H3：VSCode 里从报错行跳到源码、从源码跳到反汇编、主机调试断点；
   - H4b：二进制包自包含，跨包堆栈能说清「哪个包的哪个文件第几行」。
2. 旧固件、旧工具读到新 `.jmb` 不受影响；旧 `.jmb` 在新工具里照常可读。
3. 调试信息可选、可剥离，发布固件不为它付 Flash。

**非目标**

- 不把源码、AST、变量名表塞进 `.jmb`。
- 不做目标板上的源码级单步/变量查看（受 20 KB RAM 与串口带宽限制）。
- 不改变现有表区偏移、不改变 VM 指令编码。

## 2. 现状：JMB v4 的布局与加载边界

当前写入顺序（[writer.rs](../compiler/src/writer.rs)）：

```
[12 B 头][常量表 8B×n][名字表 2B×n][代码表 10B×n][捕获表 2B×n]
[类表 8B×n][字段名数组][方法数组][字符串池][指令流...]
```

头 12 字节：

| 偏移 | 字段 | 现状 |
|---|---|---|
| p0–3 | `JMB1` | 魔数 |
| p4 | 版本 | 4 |
| p5 | flags | 保留，写 0 |
| p6–p10 | 常量/名字/代码/入口/类数量 | 已用 |
| p11 | 保留 | 写 0 |

加载器（[jm_loader.c](../runtime/src/jm_loader.c)）只校验到类表为止的固定区与字符串池；每个代码对象的 `(off, len)` 只校验 `off + len <= 文件长度`。**指令流之后的多余字节从不检查**。这是本设计可以「只追加、不改版本」的前提。

## 3. 总体方案：文件尾的可选调试段

```
[原有 JMB v4 全部内容，偏移与字节完全不变]
[调试段 trailer（可选）]
[6 B 尾索引：u16 total_len + u32 "DBG1"]
```

- `p5` 的 bit0 表示「有调试段」。写入方带调试信息时置 1，否则保持 0（与现在的文件逐字节一致）。
- 调试段总长写在**文件最后 6 字节**，加载器从文件尾定位，不需要在 12 B 头里再挤一个偏移字段。
- 定位规则：
  1. `p5 & 1 == 0` → 不读任何调试数据（旧文件、剥离过的文件）；
  2. `p5 & 1 == 1` → 读末尾 4 B 是否为 `DBG1`，再读前 2 B 的 `total_len`；
  3. 校验 `len >= 12 + total_len`，且 `total_len >= 22`，且调试段起点 ≥ 所有代码对象 `off + len` 的最大值；任一不满足则忽略（见 §9）。
- 旧加载器不认 `p5`，且从不检查文件尾，因此**新文件在旧固件上照常运行**。
- 旧文件在新加载器里 `p5 & 1 == 0`，直接跳过，**零扫描、零 RAM**。

### 3.1 调试段内部布局

所有多字节字段小端；段内偏移相对调试段起点。字段布局已按 §12 的决定落地。

| 偏移 | 大小 | 字段 | 说明 |
|---|---|---|---|
| 0 | 4 | magic | `DBG1` |
| 4 | 1 | dbg_version | 1 |
| 5 | 1 | flags | bit0 有列号；bit1 = 每条行记录前带 1 B 文件标签（`nfiles > 1` 时置位）；其余保留 |
| 6 | 1 | nfiles | ≤ 255 |
| 7 | 1 | ncodes | 必须与头部 p8 一致（读取时自校验） |
| 8 | 2 | files_off | 文件表起点（段内） |
| 10 | 2 | codes_off | 代码目录起点 |
| 12 | 2 | str_off | 文件名字符串池起点 |
| 14 | 2 | reserved | 0 |
| 16 | … | 文件表 | `nfiles × { u16 name_off }`，`name_off` 相对 `str_off` |
| … | … | 代码目录 | `ncodes × 6 B`：`u16 entries_off`、`u16 nentries`、`u8 file_id`、`u8 reserved` |
| … | … | 字符串池 | 每个文件名以 `0` 结尾，UTF-8 |
| … | … | 行记录 | 每代码对象 `nentries` 条，见 §4 |
| 末尾 | 6 | 尾索引 | `u16 total_len` + `u32 DBG1` |

> 说明：`ncodes` 直接复用头部 p8；文件表与代码目录用段内偏移，避免依赖文件绝对地址。`u16` 足够，因为 `.jmb` 本身 ≤ 65535 B。

## 4. 源码行 ↔ 指令偏移

每条记录 = 一次「行号变化点」：

```
[u8 file_tag]          flags.bit1 时存在：0 = 沿用上一条，k = file_id + 1
u8  off_delta          相对上一条的指令流偏移增量
u8  line_delta         相对上一条的行号增量（zigzag 编码；第 0 条是绝对行号）
[u8 col_delta]         flags.bit0 时存在，列号增量
```

- 第 0 条记录的 `off_delta` 是相对该代码对象指令流起点的**绝对偏移**；`line_delta` 是**绝对行号**（1..65535）。
- 之后的记录：偏移与行号都用增量；行号增量 zigzag（`+1 → 2`，`-1 → 1`）。
- 值 `255` 为转义：后随一个 `u16` 字段（偏移或 zigzag 后的行号）。
- 记录按偏移严格递增；同一偏移不重复。
- 每个代码对象的第 0 条固定在偏移 0，行号取函数定义行；空函数也要有一条。
- 多文件（`nfiles > 1`）时每条记录前带 `file_tag`：首条必为具体文件（`k`），之后只在切换文件时写非 0；代码目录里的 `file_id` 只作该代码对象的默认起点。

**查 ip → 行**：在 `nentries` 条记录上二分，取「最后一个 `off <= ip`」的记录。
**查行 → ip**：在该文件的所有代码对象里找「第一条 `line >= 目标行`」的记录，返回其代码对象与偏移；用于跳转与断点落地。
**列号**：仅用于 VSCode 光标定位；不参与行号回查。

### 4.1 编译器侧怎么拿到这些点

- `Stmt` 已经带 `line`、`col`（[ast.rs](../compiler/src/ast.rs)）。
- `FnState::mark(line)` 在每个语句编译入口调用；同一偏移只保留最后一次（前面的语句没生成指令），同一行连续出现只留最早一条。
- 代码对象收尾时把标记交给 writer，按偏移天然有序。
- **文件身份**：不改 AST。`pack_merge::merge` 在拼接时记录「顶层语句区间 → file_id」，codegen 按区间设置 `FnState.file_id`；嵌套函数与类方法继承所属顶层语句的文件。单文件编译只有 `file_id = 0`。
- 多包时模块代码对象里不同包的顶层语句各自带自己的 `file_id`；writer 在 `nfiles > 1` 时给每条行记录写文件标签，解析侧按记录还原文件，因此依赖包顶层 `令` 不会误指根包。
- 这是纯增量改造，不触碰指令编码与 VM。

## 5. 与现有 JMB v4 表区的关系

| 项目 | 是否改变 |
|---|---|
| 12 B 头布局 | 不变；只启用 p5.bit0 |
| 常量/名字/代码/捕获/类表、字符串池 | 不变 |
| 代码对象 `off/len` | 不变 |
| 文件总长 | 变长；**体积上限按剥离调试段后的 65535 B 计算**（超了仍报 E111），调试段单独报数 |
| 加载器读取范围 | 不变；调试段只在显式开启的宿主工具里读 |
| `micc --dump` | 不变；调试查询用独立的 `--line-of` / `--lines-of` / `--debug-dump` |
| H4 包体积检查 | 按剥离调试段后的长度检查；调试段另计（见 §12 决定 9） |

一句话：**表区一个字节都不动，只在文件尾追加一段旧加载器本来就会忽略的数据。**

## 6. 是否升 JMB v5

**推荐：不升，保持 v4。**

理由：

1. 头部、表区、指令编码都没变，版本号若升到 5，旧固件/旧工具会直接拒绝新文件，收益为零。
2. 旧加载器天然忽略文件尾；新加载器用 p5.bit0 区分，不需要版本字段参与判断。
3. 现有规格写的是「布局不兼容才 +1」；尾部可选段属于兼容扩展。

代价：

- 规格文档要明确「指令流之后允许存在可选调试段」，避免第三方实现把「文件尾必须等于最后一条指令流末尾」写成硬校验。
- 将来若真需要改表区（例如常量表扩到 u16），仍应升 v5；调试段不占用这个版本号。

## 7. 开销估算

### 7.1 数据来源

用当前仓库已编译的 8 个正式示例实测（`.jmb` 字节数、代码对象数、指令条数）。指令条数为按操作数长度逐条走完指令流的结果。

| 示例 | `.jmb` B | 代码对象 | 指令条数 |
|---|---:|---:|---:|
| 你好 | 132 | 1 | 13 |
| 列表 | 450 | 1 | 79 |
| 循环 | 324 | 1 | 65 |
| 斐波那契 | 284 | 3 | 65 |
| 小数 | 1176 | 1 | 184 |
| 闭包 | 996 | 12 | 180 |
| 异常 | 1052 | 4 | 235 |
| 类 | 953 | 9 | 199 |

### 7.2 调试段大小（不含列号，varint）

固定开销：段头 16 B + 文件表 `2×nfiles` + 代码目录 `6×ncodes` + 文件名 ≈ 8–17 B + 尾索引 6 B。

行记录条数取决于「行号变化点」，只有实现后才能精确测。这里给三档：

- **下限（函数级）**：每代码对象 1 条；
- **中位（语句级）**：按指令数的 45% 估（一个语句通常编译成 2–3 条指令）；
- **上限（指令级）**：每条指令 1 条。

| 示例 | 下限 B | 中位 B | 上限 B | 上限相对 `.jmb` |
|---|---:|---:|---:|---:|
| 你好 | 49 | 55 | 69 | +52% |
| 列表 | 43 | 115 | 201 | +45% |
| 循环 | 43 | 101 | 173 | +53% |
| 斐波那契 | 51 | 119 | 199 | +70% |
| 小数 | 43 | 209 | 411 | +35% |
| 闭包 | 121 | 271 | 469 | +47% |
| 异常 | 69 | 273 | 531 | +50% |
| 类 | 106 | 268 | 486 | +51% |

小程序的固定开销占比高，大程序稳定在 **+25%～+35%（中位）**，最坏约 **+50%**。

### 7.3 对固件 Flash 的影响

当前整包（`类` 示例）：Flash 27 956 B、RAM 14 652 B，其中内嵌 `.jmb` 953 B。

- 中位调试段 +268 B → Flash ≈ 28 224 B（+0.96%）；
- 上限 +486 B → Flash ≈ 28 442 B（+1.74%）；
- 发布固件用 `--strip-debug` → **0 B**。

### 7.4 加载期开销

| 场景 | Flash | RAM | 时间 |
|---|---|---|---|
| 固件不解析（默认发布） | 0 | 0 | 0 |
| 固件解析（`JM_DEBUG=1`） | +约 300–400 B 代码 | 0（只读指针）或 +8–12 B 缓存 | 首次定位 O(log n)，n ≤ 指令数；72 MHz 下 < 1 ms |
| 宿主工具解析 | 0 | 不关心 | 读文件尾 + 建索引，毫秒级 |

**结论**：默认发布不付任何代价；调试开关只影响开发构建。

## 8. 旧文件、剥离文件与损坏文件

| 情况 | 行为 |
|---|---|
| 旧 `.jmb`，p5.bit0=0 | 完全跳过，行为与今天一致 |
| `--strip-debug` 产物，p5.bit0=0 | 同上 |
| p5.bit0=1 但尾部 magic/长度不合法 | **忽略调试段，继续执行**；宿主工具给警告 |
| p5.bit0=1，调试段与指令流重叠 | 忽略调试段，继续执行 |
| p5.bit0=1，条目偏移超出代码长度 | 该条记录忽略；宿主工具报错 |
| 旧加载器读新文件 | 不检查文件尾，正常执行 |

原则：**调试信息是附加物，永远不能阻止程序运行**。当前没有严格模式；损坏段一律忽略（§12 决定 8）。

## 9. 如何支撑 H3（VSCode 跳转与断点）

1. 编译默认带调试段；扩展可直接调用：
   - `micc --line-of <x.jmb> <代码> <偏移>`：指令位置 → `文件:行`；
   - `micc --lines-of <x.jmb> <文件|*> <行>`：源码行 → 一个或多个 `代码 偏移..偏移` 范围；
   - `micc --debug-dump <x.jmb>`：完整文件表、代码目录与行记录。
2. **诊断跳转**：`micc --check` 已给行列与错误码，扩展直接打开 `file:line`，不依赖 `.jmb`。
3. **源码 → 反汇编**：把光标 `(file, line)` 映射到 `(code_idx, offset)`，与 `micc --dump` 的地址对齐显示。
4. **运行期错误 → 源码**：`jmrun` 报错时带 `(code_idx, ip)`，用同一张表反查 `file:line`，扩展把错误行标红。
5. **断点**：断点集合保存在 VSCode 会话里，不写进 `.jmb`。`jmrun --break file:line` 启动时把断点解析成 `(code_idx, offset)`，命中即停并打印源码行。目标板不做断点（ROM 调试器不现实）。
6. **单文件程序**：`file_id=0`，文件名即入口文件名，不需要额外改造。

## 10. 如何支撑 H4（二进制包）

现状：H4a 是源码包，多个包在编译期合并成一个 `Program`，**行号保留但文件身份丢失**。这会让调试表把所有行都指回根包文件。

本轮用「合并时记录顶层语句区间 → file_id」实现了等价的文件身份，没有改 AST：

- `pack_merge::merge` 按「依赖在前、根包在后」拼接，同时产出 `files[]` 与 `spans[]`；
- `codegen` 处理每个顶层语句前设置当前 `file_id`，嵌套函数与类方法继承它；
- writer 按 `file_id` 生成文件表。

有了它：

1. **源码包**：每个包的文件都在文件表里，报错与堆栈能区分 `工具::加一` 与 `应用` 的行号。
2. **二进制包（H4b）**：`.jmb` 自包含，调试段随包分发；消费方即使没有源码，也能在错误报告里给出「包名/文件/行号」，并在有源码时直接跳转。
3. **跨包堆栈**：代码对象名已经是 `包名::名字`（H4a 的改写结果），叠加 `file_id` 就能还原完整调用位置。
4. **包体积预算**：上限按剥离调试段后的长度计算，调试段单独报数；二进制包清单可加 `调试 = true/false`，发布者自行选择是否剥离。

> 若不接受改 AST，也可以退而求其次：合并时为每个包分配「行号基址」，文件表记录行号区间。但行号会整体偏移，错误信息与源码对不上，不推荐。

## 13. 风险

1. **条目数假设**：中位 +25%～35% 是估算，真实值以 `tools/size-report.ps1` 与实测为准。
2. ~~**模块级顶层初始化的文件归属**~~ **已解决**：行记录带文件标签（`flags.bit1`），codegen 按顶层语句区间写 `file_id`，多包模块代码对象里每条记录各指各的文件。单文件不置位，零额外开销；代价是多包时每条记录多 1 B。
3. **第三方实现**：若有人把「文件尾 = 最后指令流末尾」当硬约束，带调试段的文件会被误判；规格已声明尾部可选段。
4. **体积上限**：按剥离后长度检查，调试段不会触发 E111/E130；调试段自身超过 64 KB 时报 E131，`--strip-debug` 是逃生口。
